# 方案步骤规范化与登记

日期：2026-11-10

状态：Skill 操作规则

## 首次登记与项目身份恢复

更新日期：2026-11-13

必须调用 `registrationSnapshot` 生成结构化候选，不能手工省略路线字段或把中文结果填入状态字段。初始步骤 `acceptance` 必须为 `pending`，“返回成功”等验收要求放入 `conditions[].text`；`endConditions` 是条件对象数组；`routes[].context` 必须是完整上下文对象；SHA256 使用小写十六进制。

提交前先将完整请求保存为 UTF-8 JSON，用实际插件根目录内的 `runtime/validate.mjs` 离线校验：`node <插件根目录>/runtime/validate.mjs workbench_register_plan <请求.json>`。独立 Skill 使用当前安装插件根目录的该校验器，不依赖开发仓库。只有 `valid: true` 才提交。此命令不连接服务或写入工作台。校验器报告 `validationErrors[].path`、约束与消息时，修复对应字段并重新校验；收到明确拒绝的 INVALID_INPUT 后可修正重试，不因一次参数错误就结束已授权的接入任务。若使用旧插件尚无校验器，读取实际工具 schema 校验并记录能力缺项。

更新日期：2026-11-13

用户明确要求接入并执行时，首次登记属于已有授权范围。工作台项目由登记方案生成，不要求用户先在任务岛建立项目，也不要求先有 Codex 侧栏项目 ID。

1. 读取用户方案和当前目录，按同包 `inspectWorkspace` 获取实际上下文；普通目录的 `branch`、`head` 为 `null`。读取已有本地映射；尚无映射时，用真实目录生成稳定本地 `projectKey`，用方案路径生成稳定 `planKey`，保存到当前目录的工作台同步记录。它们是本地键，不是伪造的服务 ID。
2. 已有真实 projectId 时回读它；只有本地 projectKey 时，也可将它传给 `workbench_get_project({projectId: projectKey})` 恢复真实 ID。`NOT_FOUND` 表示尚未登记，继续下一步。没有任何身份时跳过读取，不传空 ID、路径或侧栏 ID 冒充服务身份。
3. 按下文规范化方案，调用导出的 `registrationSnapshot` 生成 `mode: local` 候选，所有服务 ID 及 revision 保持 `null`。构造稳定 `eventId` 和完整来源声明。
4. 自动连接模式直接调用 `workbench_register_plan`，传 `schemaVersion: light-1.0`、`expectedRevision: 0`、`eventId`、`source`、`occurredAt`、`snapshot`、`confirmationGrant: null`。服务在登记时核验授权、候选与来源，无须访问桌面私有 confirm-publication 接口或读取管理凭据。旧版限范围连接才需要原有确认票据。
5. 保存成功响应的真实 projectId、planIds，再按真实 projectId 回读取得 stepIds、revision；随后绑定当前会话，取得开始许可，逐步执行并同步。
6. 结果未知时用原 projectKey 和 eventId 调用 `workbench_query_event` 查询 register，或重放完全相同请求；不得盲目换键重复创建。已有项目使用原身份修订；自动模式的修订也使用 `confirmationGrant: null`。

缺项目 ID 不代表应用没有连接。`INVALID_INPUT` 应先按工具 schema 修正参数或完成首次登记；只有真实工具发现、认证或连接返回相应错误时，才提示用户检查连接。不要因为缺 ID 要求用户回开发仓库或手动配置技术字段。

## 可执行规范化入口

更新日期：2026-11-11

使用同包 `scripts/normalize-plan.mjs`。先由当前聊天按原文语义识别步骤，生成 UTF-16 精确范围清单；脚本只执行已确认的编号及引用替换，不从普通列表猜步骤。清单字段为 `expectedSha256`、`nodes`、`references`、`previous`。每个 node 含稳定 `key`、`parentKey`、原编号 `originalCode`、`title`、`locator`、显式 `order`、`dependsOn`（固定本地键数组）、`acceptance`、`codeRange: {start,end,expected}`；新增中插项另含 `insertAfterKey`。references 每项含相同范围及 `targetKey`，覆盖依赖表、Mermaid 标签、文内及已授权外部引用。未确认范围保留待确认，不执行猜测性替换。

`node <Skill绝对路径>/scripts/normalize-plan.mjs <清单.json> <原文.md> <候选.json>` 默认仅生成含日期、前后 SHA256、文本、映射及差异的候选。order 为各父作用域内唯一正整数，插入后按实际位置重排 order，不改已有编号和固定身份。相同来源再次处理保持编号；已有映射必须完整传入，`stepId` 原样保留，插入使用锚点后缀。源变化、缺失或循环依赖、身份删除及重叠范围明确拒绝。需要写回时使用导出的 `applyNormalizedFile`，保留 Git 旧版本并重检来源；其他编辑器出现并行变化时停止合并，不覆盖用户内容。

导出的 `registrationSnapshot` 将包含逐项验收的结果转换为当前 `light-1.0` 本地候选，未登记服务 ID 全部为空。对已经登记方案使用服务现有 projectKey、planKey 和步骤 key，保留既有编号、必要验收与依赖语义；真实 ID 由发布成功回读取得。先读取工具 schema 校验候选，再走原生确认发布，不把文本处理成功当成服务已登记。重复发布使用同一精确请求和 eventId；来源或内容改变属于新修订。

## 读取与确定步骤

读取用户指定方案、引用的当前权威资料及现有工具映射，确定正式执行步骤、顺序、依赖、验收、终点和当前来源版本。章节标题、普通列表和验收子项按其语义分类。已有清晰顺序时直接采用，涉及并行时采用方案的显式排列。顺序或步骤边界含糊时先完成明确部分的提取，向用户确认歧义后再改受影响部分。

对用户授权接入的方案文件，保存修改前 SHA256 和可恢复版本定位。已纳入 Git 的旧版本可用提交加差异定位，未提交内容或外部文件先保存日期标记的 UTF-8 原文副本，避免遗漏用户修改。

## 分配与更新引用

首次规范化将总阶段分配为 A、B、C 等字母，超过 Z 使用 AA 等延续。阶段内细分步骤按父阶段分配 A-01、A-02、B-01 等，数字至少两位，超过 99 使用三位。同一方案的阶段字母统一分配，跨工作树沿用，保存父阶段与细分步骤的层级和依赖。已登记步骤复用工具编号与固定 stepId，新插入按锚点分配 A-02-a、A-02-b，顺序另存。取消保留历史编号，拆分、合并及替代保存旧新关系。

先形成包含来源位置、原编号、工具编号、标题、依赖及 stepId 的映射。服务 ID 未取得时使用本地关联键，登记成功再绑定。原编号重复时按章节作用域和来源位置区分。步骤缺少旧编号时记录原始标题及位置。

例中“准备阶段”和“界面阶段”可映射为总阶段 A、B，会话分别为 `[A] 数据准备` 和 `[B] 界面展示`。A 内部细分为 A-01、A-02 等，B 内部细分为 B-01、B-02 等。同一会话负责所属阶段的一组细分步骤。总阶段数量和细分步骤数量分别统计。

按语义更新执行步骤标题、依赖表、Mermaid 标签和步骤引用。检查链接锚点、图节点标识及引用一致性，保留正文含义、依赖和验收要求。使用精确位置或有作用域的替换，避免全文件数字替换。外部引用按实际授权更新，其余记录待处理位置。

写入前再次比较源文件版本及未提交内容。发现并行变化先重读合并。提交修改后复查编号唯一、依赖存在、无环、全部步骤和验收保留。第二次处理同一版本应保持原编号和映射。

## 发布同一来源版本

从规范化后的文件提取结构化路线，计算修改后 sourceHash，保存路径、日期或版本、步骤映射、工作树分配及确认问题。先按实际 MCP 能力保存和校验草稿，再按服务端确认授权发布。需要确认凭据时展示具体差异并使用有效授权。

草稿成功只记录草稿状态，发布成功后将真实 planId、stepId 及 revision 写回映射。服务不可用时保留文件修订和待同步资料，下次先检查原事件是否已提交，核对 sourceHash 后恢复。用户修改方案后重新生成草稿及差异，保持来源与已发布版本可追溯。
