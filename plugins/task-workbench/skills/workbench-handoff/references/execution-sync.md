# 执行状态、回执与接续

状态：Skill 操作规则

## 开始本次执行

更新日期：2026-11-13。对话中没有显式显示 threadId 不等于身份不可用。必须先在当前执行目录实际运行 `node <Skill目录>/scripts/binding-request.mjs --context`，它会从命令环境 CODEX_THREAD_ID 自动读取真实会话 ID，本地宿主 ID 为 local，并核验目录。不得仅阅读源码后声称宿主没有提供身份，也不要要求用户填写身份。检查成功后必须继续回读已登记项目并生成完整绑定请求，不能结束在身份检查说明。检查失败时报告实际命令、具体错误及输出，再按真实缺项处理。

旧回复中的 UNKNOWN_RESULT 不能无限继承为当前阻塞：先回读原项目最新 bindings、executions。仅在存在已保存的真实 eventId 或未结束执行时按对应恢复流程核验；没有原事件键时不能构造空键查询，更不能把历史自述代替当前服务证据。已登记方案复用原身份，禁止重复登记。

更新日期：2026-11-13。绑定前保存最新 get_project 返回的 snapshot，使用同包 `scripts/binding-request.mjs` 生成完整绑定请求：在真实执行目录运行 `node <Skill目录>/scripts/binding-request.mjs <snapshot.json> <稳定eventId> <bind.json> [planId]`。脚本从当前 CODEX_THREAD_ID 获取真实会话，核验当前目录并使用服务返回的项目、方案、步骤及版本。不要用空对象调用绑定，也不要用空 eventId 查询。调用前用插件 `runtime/validate.mjs workbench_bind_context <bind.json>` 校验，确认有效后保存精确请求再提交；任何执行写入请求均须同样核对完整身份和原事件键。结果未知时查询刚保存的真实 eventId，服务恢复后复用原请求与身份，不能重复登记已成功的方案。

更新日期：2026-11-13

先核验用户当前项目的实际目录，不要求它是插件开发仓库。普通目录可正常登记方案、绑定会话、开始执行和同步状态：用 `inspectWorkspace` 得到真实路径，`branch: null`、`head: null` 表示已核验的非 Git 目录。Git 检查不适用时记录“不适用”，不能据此拦截普通任务，也不要初始化仓库或编造 `main` 分支。有 Git 时继续核验根目录、分支和 HEAD；Git 分支、工作树及合并任务必须满足真实 Git 条件。以下“目录与分支”在普通目录模式下指真实目录及无 Git 的现场状态。

原生 Git 工作树允许 detached HEAD，此时 `branch: null`、`head: <真实提交哈希>`，不是非 Git。`binding-request --context` 自动保留此区别；服务确认时核验起始提交，执行期间允许在同一 detached 工作树正常提交，不能填造具名分支或将 HEAD 清空。来源项目目录与实际执行工作树分开，绑定引用实际执行目录。

更新日期：2026-11-12

自动连接模式中，普通 `workbench_bind_context` propose 成功并返回 `state: confirmed` 即已完成绑定，直接采用回执版本，不再要求用户确认 ID 或 JSON。接手旧执行仍提交原有 propose/confirm 两个事件，confirm 使用 `confirmationGrant: null`，服务自动核验接手范围和真实 Git 目录分支。旧版限范围授权才需要其原生确认凭据；下文原生绑定确认要求仅适用于旧模式。

读取当前方案、服务快照和台账，检查本次范围、绑定版本、真实目录与分支、全部必要前置及验收要求。前置不满足时保留待执行并列出等待对象。已获授权且前置满足时，登记逻辑执行开始与当前步骤进入执行中，保存服务返回的 executionId、版本及事件键。

开始许可必须取得服务确认。工具不可用时保存待同步资料，暂停当前步骤实施，列出服务、发布或绑定等待条件。开始登记与步骤 running 使用同一逻辑事件的适配或分别关联，避免重复建立执行批次。

## 前置依赖拦截

更新日期：2026-11-10

首次开始、步骤切换、阻塞恢复及换聊接续时，先读取当前权威方案、最新服务快照和适用验收证据，核对全部必要前置、绑定与授权。服务中的依赖与方案不一致时先核对修订来源。前置 completed 还需有当前版本适用的必要验收通过依据，历史交付或执行者自述需进一步核实。

全部条件满足后提交开始或恢复事件，取得成功回执并核对当前执行身份及步骤状态，再进入实施。接续已有执行时先查询其有效性及未确认事件，复用有效 executionId。开始响应丢失时查询或重放原事件，结果未知期间暂停实施。

前置未满足、取消后尚无替代承接、状态或证据无法确认、服务门禁拒绝、绑定失效、版本冲突未解决及开始结果未知时，停止当前步骤的代码与业务文件修改、实施命令、构建测试、发布及其他实施性外部操作。允许读取资料、查询状态、核验证据和保存必要的拦截及恢复记录。生成交接指令时携带此门禁要求。

未开始步骤保持 pending，记录等待对象；已运行步骤的前置失效时暂停实施，按实际服务能力提交 blocked，失败或未知时保留真实同步状态。解除等待后重读全部前置与阻塞，重新取得有效执行许可。

用户直接要求“执行 E”时仍检查 D 的出口。D 未通过则输出“E 暂不可执行”，列出未满足前置、缺失证据、当前状态和解除条件，F 继续等待 E。用户明确改变依赖时按方案修订流程记录差异、影响和授权，完成校验及发布后重检。收到提前执行要求时保持原依赖门禁有效。

拦截发生后，可给出核对前置剩余事项的建议，执行其他步骤继续依据其授权范围判断。Skill 负责行为约束，宿主实施工具的强制许可校验单独验收。

完成前检查逐项验收，检查未执行或证据不足时保留待核验说明和实际业务状态。服务端规则判定有效完成，状态请求成功与验收证据分别记录。

## 同步和结束

### 验收与交接对应

更新日期：2026-11-10

五状态、验收记录、执行结束原因及 A—G 结论分别保存。代码交付后必要验收未完成时，保留执行中并记录待核验，交接选 B；需要外部条件且无法继续时登记阻塞。验收发现缺陷继续原步骤修复，选 A；原步骤已完成时显式 reopen。本站验收通过后提交 completed，等待其他线前置时选 C，下一站全部前置满足时选 D，实际开始后再将后继更新为 running。

等待用户时记录确认对象和解除条件，已开始且无法继续的步骤进入 blocked，未开始步骤保留 pending。验收确认选 B，范围或方案冲突选 G，其他情形按本站条件判断。一次聊天或执行结束时按实际状态提交回执，任务线全部条件满足选 E，项目全部条件满足选 F。A—G 依据全局范围核对。

必要用户体验确认列入验收要求。成功保存后回读步骤及证据，分别记录提交结果与验收依据。

每次逻辑操作建立稳定事件键，重试复用原键。请求已发送但结果未知时先查询或重放原请求。工具明确拒绝时记录原因，读取新版本或补齐问题后建立相应新操作。撤销授权后停止该授权下的新写入，保留可用范围内的本地交接资料。

结束本次执行时提交一次逻辑结束回执，包含完成本次范围、等待用户、阻塞、失败或取消等实际原因，附交付物、逐项验收、证据、未决项和相关步骤快照。快照携带当前版本，由服务校验并行更新。按通用模板输出完整回执，实际执行批次和整个方案的完成状态分别记录。

## 接续与中断

更新日期：2026-11-11

换聊继续未结束执行时，`workbench_bind_context` 的 propose/confirm 可携带 `takeover: {fromBindingId,expectedBindingRevision,executionIds}`。完整核对旧责任范围和全部未结束执行，原生确认入口核验新会话、实际目录分支及相同接手意图。成功确认在同一事务撤销旧责任、确认新责任并转移所列原 executionId，保存原绑定版本和执行快照。不得自行预留新 executionId 替代仍有效的原执行；不能核对完整旧范围时先明确分配，不吞并无关责任。

已提交旧事件按原键回放仍返回原回执；接手后旧绑定的新事件拒绝实时写入，并保存历史待核对记录。使用旧主体在原作用域 `workbench_query_event({operation:'update',eventId,...})` 查询时，`state: pendingReview` 表示迟到历史等待核对，不是已提交或可自动重放。新会话继续沿用原 executionId、当前新 bindingId/bindingRevision 和最新 revision。宿主标题、业务状态、验收状态、同步状态及执行结束原因分别保存。

新会话先读取现有版本、原绑定、执行和未确认事件。跨会话继续同一次执行时沿用 executionId，重新核对责任绑定。接手建立有效新绑定，迟到结果按历史待核对处理。

异常中断后的结束时刻和结果依据已有证据补记，未知项保留未知。界面最后更新时间或会话停止只能用于定位核对范围。未到达服务端的事件由本地待同步记录恢复。


## 未完成、失败与停止反馈

更新日期：2026-11-11

执行任务时，交接结论 A 表示本站尚未完成。已获授权、前置和执行许可有效、仍有可执行的必要修复或核验时，继续当前步骤并检查修复结果。提交部分代码、单次检查失败或已经能够生成回执，均不能单独作为结束本次执行的依据。仅请求核对或生成指令时，沿用该请求的输出范围。

确需结束未完成的执行时，按现有固定回执字段逐项写明以下内容。

| 现有字段 | 必须包含的反馈 |
|---|---|
| 实际交付 | 本次实际修改的文件、行为和实现版本；未修改时写明实际完成的调查或操作 |
| 提交及验证证据 | 实际执行的命令或操作、环境与版本、结果及证据路径；记录关键报错并脱敏，区分未执行、执行失败和检查不通过 |
| 各项验收条件及结果 | 失败对应的原验收条件、预期与实际、已验证原因及仍待验证的假设；根因未知时明确记录未知 |
| 当前阻塞 | 逐项列出剩余工作、依赖、等待对象、解除条件，以及停止本次执行的具体原因；仍可执行的剩余工作单独标明 |
| 结束结论 | 使用中文含义说明本站状态，给出恢复动作、责任对象及是否实际派发；交接结论、方案阶段和工具同步状态分别记录 |

例如应写“D 阶段未完成，交接结论 A；D-03 私有传输检查失败，错误与证据见……；本次停止因……；解除条件为……；接续先执行……”。单写“结论 A，继续本站”无法满足失败反馈要求。

同一失败再次出现时，关联原问题和已有尝试，记录本次方法、版本、结果及与上次的差异。先依据错误和证据调整假设，再决定修复或重试。涉及外部写入的重试复用原事件键并先查询未知结果。连续无进展时采用项目已确认的评估阈值，记录阻塞及需要的决定。

开始许可失效、外部依赖、人工确认、权限缺失、用户暂停或运行资源中断等停止原因按实际发生情况记录。资源中断后的恢复记录只补充可核实的信息。已自动发送续执行指令时记录真实目标和结果；尚未派发时明确等待谁触发。Skill 结束后的自动唤起和新聊天派发由实际调度能力承接，其运行结果单独核验。
