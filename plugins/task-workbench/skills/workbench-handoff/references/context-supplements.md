## 固定映射与宿主操作日志

更新日期：2026-11-11

同包 `scripts/context-ledger.mjs` 提供 `folderName`、`executionTitle`、`inspectWorktree`、`recordMapping` 和 `runHostOperation`。保存 `planKey/planId`、`stepKeys/stepIds` 集合、`threadId/hostId`、`hostProjectId`、目录、分支及工作树序号。名称改变追加 mappingHistory，不以同名会话合并固定身份。真实目录由 Git 工作树根、实际分支和 HEAD 核对；子目录或错误分支不能当成工作树根绑定。

宿主工具由当前聊天发现并调用，不由脚本伪造接口。将真实工具作为 adapter 注入 `runHostOperation`，或以相同结构记录实际返回；每项包含稳定 operationId、意图指纹、pending/succeeded/failed/unsupported、目标固定 ID 和 attempts。重试同键异意图拒绝；成功结果复用；部分失败保存已经取得的目标 ID。掉响应保持 pending/resultUnknown，先 reconcile 原 operationId；没有确认未提交前不重复创建。新增聊天只有用户明确要求创建后执行。列表能力与创建项目、改名、移动和跳转分别核对，不以创建侧栏分区代替项目创建，也不把打开文档当作跳转聊天。

操作日志放在当前台账旁的同步记录或证据 JSON，不写入凭据。宿主项目创建缺接口时先按 [自动准备宿主项目](coordination.md#自动准备宿主项目)检查可用且被允许的界面路径，不能直接转交人工；项目改名缺能力时保存建议名称。分支或方案名称变化重新计算名称，另建改名事件并保留原序号、目标 ID 和历史。

## 会话组织

更新日期：2026-11-13

普通文件夹也是有效用户项目，不必位于本插件仓库。用 `inspectWorkspace` 读取实际目录：非 Git 目录的 `branch`、`head`、`repositoryRoot`、`gitCommonDir` 均为 `null`，绑定上下文使用 `branch: null`、`head: null`。自动绑定仍直接返回 `state: confirmed`，执行期间继续核验目录存在及非 Git 状态。`inspectWorktree` 专用于必须使用 Git 的分支、合并或多工作树协调，保持严格核验。下文关于 Git 根、分支与 HEAD 的要求适用于 Git 项目；普通目录不因 Git 不适用而停止。

总方案直接执行时文件夹使用方案名，内部会话采用 `[A] 数据准备`、`[B] 界面展示`。每个会话对应原方案的一组工具步骤，组内步骤在该会话连续执行。

多工作树时文件夹采用 `1️⃣ 方案名 · codex/实际分支`，每个工作树一份文件夹，会话在同一方案内统一分配 A、B、C。一个工作树可负责 A、C，另一个负责 B、D，执行依赖仍由方案决定。序号稳定登记，超过九个使用逐位数字表情。会话主题与实际任务一致。

使用实际工作区工具查询目录与 Git 分支，工作树创建遵循用户已有授权。使用结构化 `workbench_bind_context` 的 propose 提交步骤集合、会话组织编号、外部身份、目录及分支。保存 bindingId、bindingRevision、待确认问题和拟定名称。

更新日期：2026-11-12

任务岛已开启当前应用的自动连接时，`propose` 由服务核验真实 Git 目录和分支，直接返回 `state: confirmed`。此时保存返回的 bindingId/bindingRevision 并继续执行，无须用户填写 ID、路径或确认 JSON，也不要再次提交 confirm。接手旧执行时仍按原 propose/confirm 两个事件提交，confirm 携带 `confirmationGrant: null`，服务自动核验完整旧责任与接手意图。若连接未开启，提示用户到任务岛 MCP 页开启当前应用的连接，不要要求用户编辑凭据或技术字段。

多应用同时连接时，各应用使用独立凭据和 `WORKBENCH_LIGHT_APP` 标识。Codex 沿用原配置路径，其他应用使用各自连接目录。应用之间不能直接复用其他应用的已确认绑定；接手仍需沿用原执行身份并核对完整范围。任务归属由服务记录的绑定主体确定，不能按标题、分支名或客户端自报文字猜测；没有可信归属的历史任务保留为未分配。MCP 工具可用不等于宿主具备项目创建、聊天跳转等专有能力。

接入方式更新日期：2026-11-12。未接入时，用户在任务岛复制对应应用的接入指令，再发送到该应用的对话窗口。执行 Agent 先运行本机助手的 --describe 获取无令牌配置，按本应用真实格式安装 MCP 和配套执行说明；配置校验后运行 --complete 自动开启连接，无须用户返回点击。请求仅限所选应用且 30 分钟有效，重复执行复用已有连接；断开后旧请求不能重新打开连接。不要输出请求文件中的票据或连接凭据，也不要读取管理令牌。--complete 成功只代表本机连接已开启，真实宿主重载并发现工具后才能报告接入；需要新会话时准确说明。

旧版限范围授权的 confirm 仍使用已认证 UI 签发的确认凭据。仅在实际工具返回要求时采用旧流程；自动模式核验失败先核对 Git 分支和最新服务版本，不绕过失败。来源声明和已确认身份分别保存。执行引用有效绑定版本，撤销后拒绝新写入。重分配保存接手关系与旧责任执行，一步同时只允许一个有效执行责任绑定。

## 宿主操作

检查当前环境能否列项目、创建项目、改名、移动会话和跳转，按已有授权逐项执行并记录结果。MCP 负责关联及命名意图，宿主工具执行实际操作，工作区工具管理 Git 和目录。只有真实返回的目标 ID 才登记为已创建。

创建和移动以稳定 operationId 记录 pending、succeeded、failed 或 unsupported。重试先核对已经成功的项目及序号，部分失败保留成功结果。项目创建先自动复用、原生添加或在电脑技能允许时通过界面添加，真实列表回读后登记固定 ID；全部自动化路径受限时才提供最少人工动作和具体原因。新增会话或文件夹按任务授权范围进行。

## 补充事项

更新日期：2026-11-11

真实所有者对“待确认→待规划”和必要事项取消提供原生「确认补充事项」入口。先展示实际事项、来源与规划范围；取消时明确 `cancellationHandoff` 替代或承接安排。用户已有授权覆盖这些内容时按范围处理，缺少决定时等待用户；不能用测试授权代替真实用户决定。

入口提交 `{principal,input,acknowledged:true}` 到私有 `/api/light-access/confirm-supplement`，签发绑定精确项目、来源、版本、动作和内容的短期凭据。MCP `workbench_record_supplement` 的对应 update/cancel 请求携带 `confirmationGrant`。普通插件凭据不能调用该私有入口，内容或版本变化须重读并重新确认。事项 create 的稳定 eventId 和 repairId 继续沿用；linkPlan 须确认规划且关联授权完整，resolve 须引用关联方案已提交的必要交付证据。

仅解除该 supplementId 对应的阻塞，保留其他事项、人工及依赖阻塞；全部前置与阻塞检查后才能恢复 running，完成来源步骤仍检查来源自身验收。取消必要事项的承接决定保存在受控确认请求及历史中。

原验收所需的普通调试、重试和小修复保留在原步骤内。独立目标、单独安排或验收的事项经实际工具 `workbench_record_supplement` 登记，使用 create、update、linkPlan、resolve、cancel 等 schema 支持的动作。

记录来源步骤、目标、是否阻塞来源、状态及旧 repairId。旧 RepairCase/RepairAttempt 作为历史引用保留，含义不明的案例先待人工分类。

新事项进入待确认，用户确认规划后进入待规划。方案形成并取得执行范围授权后进入执行中，交付及验收满足后 resolve。取消需原因、替代或承接说明。阻塞事项创建与来源阻塞同步，完成或取消后解除对应阻塞来源，再检查原步骤全部前置与验收。

独立事项规划会话先展示一句目标、来源和阻塞说明，按用户现有授权推进。仅授权写方案时完成规划及可审阅交付，实施范围单独依据用户指令判断。

### 分类样例与调整

更新日期：2026-11-10

修复原要求的保存失败、补齐原验收检查和自动重试留在原步骤。新增原方案未要求的导出功能等独立目标登记补充事项。外部模块需独立修复才能继续时，登记补充事项并标记 blocksSource，同时保存来源步骤的对应阻塞。含义不明时保留待确认分类和判断依据。

分类变化保留原 repairId、supplementId、来源步骤、历史记录和调整原因。同一事项重试沿用身份；转为独立事项时建立关联，归回原步骤时记录归并依据和承接安排。

resolve 或 cancel 仅处理该事项对应的阻塞来源。完成核对关联方案必要交付，取消必要事项明确替代承接。随后重读全部阻塞与前置，满足恢复条件后更新来源步骤为 running，完成来源步骤时仍检查其自身验收。
