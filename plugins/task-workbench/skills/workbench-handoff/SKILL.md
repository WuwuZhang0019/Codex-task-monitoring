# 工作台方案接入、执行与交接

日期：2026-11-10

更新日期：2026-11-12

更新日期：2026-11-13

用户要求“接入并执行”且当前项目尚无工作台 ID 时，先按 [首次登记流程](references/plan-registration.md#首次登记与项目身份恢复)建立本地候选并调用 `workbench_register_plan`，不要先用空 projectId 读取，也不要让用户去任务岛手工建立项目。自动连接已开启时登记使用 `confirmationGrant: null`，成功响应会生成真实项目、方案、步骤 ID；随后回读、绑定并开始。Codex 侧栏项目与工作台项目是不同身份，普通测试不需要另外创建侧栏项目。已持有本地 projectKey 时可用它调用 `workbench_get_project` 恢复真实 ID。

状态：支持核对/生成与授权协调两种模式；实际宿主能力、安装来源和原生派发验收分别记录

## 选择当前工作

按用户请求选择流程，沿用已授权范围。输入为方案路径，可附当前台账、回执、工作树和绑定信息。

| 请求 | 读取参考并执行 |
|---|---|
| 接入方案、修改步骤编号、导入路线 | [方案规范化与登记](references/plan-registration.md) |
| 执行指定步骤、更新状态、结束或接续 | [执行与同步](references/execution-sync.md) |
| 分配工作树、会话归类、独立补充事项 | [关联与补充事项](references/context-supplements.md) |
| 核对下一步、生成指令、核验回执、结束交接 | [路线核对与交接](references/handoff-workflow.md)及[通用模板](references/handoff-template.md) |
| 在对应项目创建执行聊天、派发并跟踪、接续多开发线 | [授权协调执行](references/coordination.md)，先选择模式并保存授权范围 |

方案编号与引用的确定性变换使用本包 `scripts/normalize-plan.mjs`；固定会话映射、命名和宿主操作重试使用 `scripts/context-ledger.mjs`。输入、脚本入口及发布分别见对应参考。先按语义确定步骤边界，脚本不猜测自然语言中的执行范围。

仅请求核对或生成指令时按交接流程输出。用户授权接入方案时执行编号规范化和登记，授权执行任务时按范围实际开展并上报。任务过程中有新输入时保持当前目标，结合新约束推进。

## 两种模式与持续授权

日期：2026-11-12

A 仅核对/生成：只读资料并输出指令，不创建聊天、发消息、登记路线、绑定或开始执行。生成指令、历史方案和其他聊天的请求都不能转化为派发授权。

B 授权协调：用户明确允许按方案在对应项目创建聊天、派发、收集和接续后，读取 [协调流程](references/coordination.md)，在原任务授权范围内持续推进。保存原始人类授权出处，分别记录登记/接入、创建聊天、指定目标派发、收集、回报与接续权限；新工作树、推送、发布及真实供应商调用单独判断。不要每创建一聊或每条既定派发重复确认。

侧栏项目 ID、来源目录、实际仓库、工作树、分支、threadId/hostId 与工作台 projectId/planId/stepId 分别保存。默认复用现有项目和工作树。当前 `create_thread` 的 `local` 使用保存项目的来源目录，schema 没有指定已有工作树路径的参数；来源目录不同于预期工作树时返回能力缺项，不用 `worktree` 偷建新目录，不在提示词里指定路径后声称原生绑定成功。

协调日志沿用 `context-ledger.mjs` 的操作身份和未知结果规则，`scripts/coordination-cli.mjs` 提供持久检查点及两段原生调用。服务新增 `workbench_get_coordination` / `workbench_save_coordination` 后可保存同一日志，不建立另一个业务执行或调度系统。必须先发现实际工具，旧所有者缺少新接口时保留本地恢复记录并报告同步缺项。

## 执行聊天命名

更新日期：2026-11-10

收到本次已授权执行指令后，从首行“开始执行”后提取完整任务名称作为当前聊天标题，去除首尾空白及句末作为行文结束符的句号，保留圈号、项目名、分隔符和任务名。例如“开始执行② 轻量路线工作台 / B 路线与存储。”对应标题“② 轻量路线工作台 / B 路线与存储”。该标题约定优先用于执行聊天，组织编号与绑定映射另行保存。

发现可用的 set_thread_title 宿主工具后调用，当前聊天可省略 threadId，以真实返回结果记录改名是否成功。已有相同标题时保持幂等。新执行指令进入另一主步骤时使用该指令的新标题，普通调试沿用当前标题。工具不可用或调用失败时保留建议标题及实际结果，继续已授权任务。

生成 A/B/D 执行指令时，在代码块中携带相同的命名要求及提取后的完整标题，使执行聊天能独立完成改名。只生成指令的聊天在生成阶段保留自身标题。

## 执行前依赖门禁

更新日期：2026-11-13

用户项目目录与插件源码、安装目录相互独立。普通任务和返回值测试可在用户当前普通文件夹内登记、绑定和执行，不要求切换到开发仓库，也不要求 `git init`。使用同包 `scripts/context-ledger.mjs` 的 `inspectWorkspace` 核验真实目录；非 Git 目录将 `branch`、`head` 记录为 `null`，仓库与 Git 公共目录也为空，不伪造分支或 HEAD。已有 Git 仓库仍核对根目录、分支与 HEAD，仓库核验异常不能降级为普通目录。只有方案涉及 Git 分支、工作树或合并时，才把 Git 条件作为该操作的必要前置。方案可来自用户附件或指定路径，不依赖开发时的绝对路径。

更新日期：2026-11-10

每次开始、切换、恢复或接续步骤，按 [执行与同步](references/execution-sync.md) 的“前置依赖拦截”核对最新状态及验收，取得有效开始或恢复许可后开展实施。前置未满足、状态无法确认或开始结果未知时暂停当前步骤实施，保留等待对象和解除条件。用户直接要求执行后继时仍执行该检查。生成执行指令时携带门禁规则，要求执行聊天在修改文件和运行实施命令前完成核验。

## 当前方案与三种身份

在用户指定项目目录中读取用户提供的方案与实际台账。以下路径仅供本插件自身开发使用：`docs/03_轻量路线工作台/00_执行入口/00_新路线实施总纲与接口决定_2026-11-10.md`。用户项目不要求存在此文件；普通测试直接以用户给出的测试方案为准。

总方案阶段使用 A、B、C 等字母，本项目七阶段为 A—G。阶段内细分步骤使用 A-01、A-02、B-01 等，跨工作树保持父阶段和编号稳定。会话编号对应总阶段执行分组，可承接所属阶段的多个细分步骤。工作树文件夹序号 1️⃣、2️⃣、3️⃣ 表示归类顺序。保存它们与 planId、stepId、会话固定 ID、工作树目录及 Git 分支的对应关系。

## 先检查实际能力

更新日期：2026-11-10

发布与加载时核对实际 Skill 来源、插件版本、源码提交和入口及参考文件 SHA256。独立安装与插件缓存出现同名入口时，核实本次加载来源；安装与重载结果分别记录文件一致性、Skill 可见和实际流程行为。发布核验要求见本项目 Skill 模块方案的“源码、发布与安装版本一致性”。

读取 MCP 实际暴露的工具、参数 schema 和 supportedCapabilities，再选择调用方式。本项目源码中的新接口设计为 `workbench_update_step_status`、`workbench_record_supplement` 和 `workbench_bind_context`。它们的可用性按当前宿主实际发现结果判断。旧工具仅在其 schema 和业务语义能表达当前操作时作为适配入口。

只读 probe 返回的隔离项目用于连接验证。业务 ID 来自授权项目和真实保存结果。尚未登记的服务 ID 留空，使用有作用域的本地关联键保存待同步资料。schema 未接受的字段留在本地记录中。

写入统一保留稳定 eventId 或服务要求的 idempotencyKey、expectedRevision 和资料来源。成功回执后记录已同步版本。响应丢失保留提交结果未知，通过原键查询或重试同一请求，确定新状态后再发新操作。版本冲突先重读并核对用户范围及并行改动。

## 工作记录与结束输出

开始前核对仓库、工作树、Git 分支、HEAD、未提交改动和资料版本。来源文件及历史回执作为核对资料，当前用户授权决定操作范围。

登记或执行时，在用户指定台账内保存资料映射和同步记录。未指定时使用项目当前台账旁的 `workbench-sync.md`，已有文件先读后追加。记录日期、操作、原文步骤、工具编号、会话、实际状态、同步状态、事件键及证据位置。凭据使用宿主管理的安全存储。

执行结束说明本次结果、验收依据、未完成事项及是否成功同步。整体完成依据所有必要步骤、依赖和验收要求。交接流程保留 A—G 结论及十八字段回执，圈号和总步数按完整方案的明确执行顺序核对。

所有新增或修改文档使用 UTF-8，包含 YYYY-MM-DD 日期。按项目既有 Git 规则提交实际变更，保留无关及并行工作。

## 当前任务推理等级推荐

日期：2026-11-10

在首次接入、开始执行或生成下一步指令时，根据当前步骤的歧义、跨模块依赖、故障定位难度、变更影响及验收复杂度给出推荐。任务范围发生显著变化时重新评估，同一任务内保持简短，避免重复提示。

官方部署检查清单列出五个推理档位 `low`、`medium`、`high`、`xhigh`、`max`。GPT-6 Sol 和 GPT-6 Luna 另支持 `none`，合计六种取值；GPT-6 Astra 和 GPT-6.1 Sol 支持前述五档。模型支持情况按当前官方文档与实际宿主确认。

| 任务特征 | 推荐推理等级 |
|---|---|
| 提取、分类、路由、常规文字修改或明确单点操作 | `low` |
| 常规功能实现、局部修复、明确验证路径的方案编写 | `medium` |
| 跨模块推导、事务与恢复排查、复杂依赖或根因诊断 | `high` |
| 复杂任务已有代表性评估证明进一步推理有质量收益 | `xhigh`，同时说明评估依据及额外耗时、资源取舍 |
| 最困难任务已有评估证明最高档位值得额外消耗 | `max`，同时列出相对较低档位的收益证据 |

生成执行指令时，必须在可复制代码块外、紧邻代码块之前显示完整推荐行，例如“建议模型为 GPT-6.1 Sol，推理强度为 high。依据为本次需要核对跨模块契约及回归结果。”按本次任务填写明确模型、明确档位及一句依据，模型选择见“面向用户的模型与推理强度推荐”。输出前逐项检查模型名称、推理档位、依据和展示位置，缺项时补齐后再交付。

保持既有回执字段顺序。单凭文件多、耗时长或多轮失败不足以推荐 xhigh 或 max。

当前模型未知时给出明确条件建议，例如“建议 high，待核实所选模型支持情况”。已知该档不可用时根据实际支持集合调整并说明原因。none 仅在模型明确支持且任务适合关闭推理时评估使用。用户对耗时与资源消耗的偏好纳入选择。

推荐由用户选择采纳。实际调整设置需要用户授权及宿主支持，并记录真实结果。推荐完成即可继续已授权工作。验收覆盖简单任务、复杂故障、范围变化及可用档位未知四类场景，检查推荐依据与任务一致。

模型支持及推理预算机制以当前官方资料和宿主能力为准。资料核对日期为 2026-11-10。[OpenAI 推理模型文档](https://developers.openai.com/api/docs/guides/deployment-checklist)

## 面向用户的模型与推理强度推荐

更新日期：2026-11-11

首次接入、开始执行或生成下一步执行指令时，为用户同时推荐一个明确模型和一个推理档位，并给出一句与本次任务有关的依据。该要求更新上文仅显示推理等级的输出约定。推荐行放在可复制指令代码块外、紧邻代码块之前，采用“建议模型为 GPT-6.1 Sol，推理强度为 high。依据为本次需要核对跨模块契约及回归结果。”这样的完整表述，按实际任务填写。

优先依据用户当前可选模型、明确偏好与实际任务选择。用户已经指定模型时沿用其选择并推荐适用强度。可选范围未知时说明推荐模型的可用性待核实，结合实际宿主支持的推理档位输出。模型和推理支持集合依据当前官方资料核对。

模型选择的起点如下，按任务证据及用户对质量、耗时和资源的偏好调整。

| 当前任务 | 模型选择起点 |
|---|---|
| 复杂开发、跨模块实现和回归，需要兼顾耗时与资源 | GPT-6.1 Sol |
| 含糊问题、冲突证据、深度诊断或复杂架构判断 | GPT-6 Astra |
| 明确目标的截图分析、电脑操作和局部代码修复 | GPT-6.1 Terra |
| 范围清晰的简单整理、提取和重复处理 | GPT-6 Luna |

推理强度沿用前节按任务复杂度评估。失败后先核对错误、证据、提示与执行条件，再判断换模型或提高强度是否能解决具体问题。推荐由用户选择，完成推荐后继续本次已授权工作。执行指令携带相同建议供接手续用，实际设置变化记录真实结果。

输出前检查模型名称、推理档位、任务依据和代码块外的展示位置均已具备。验收包括复杂开发、视觉操作、简单整理、用户指定模型及可用模型未知五类情况，逐项核对推荐与条件一致。

模型定位参考资料核对日期为 2026-11-11。[OpenAI 模型选择指南](https://developers.openai.com/api/docs/guides/model-selection)
