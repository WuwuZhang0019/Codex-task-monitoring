## 1. 权威关系与结束条件

README 项目总方向为目标依据。本总纲统一六份方案的执行顺序、补充规则和组合验收。01 为需求背景，02 为桌面主线，03 为动效专项，04 为组合业务，05 为接入契约，06 为插件及修复回归专项。各文件中的历史现场和已完成文档记录保留，不代表实现完成。

实际派发以本文件 U01—U08 为唯一总路线。D、FX、C、CX、LP 保留为来源定位与验收索引，不再分别重复派发整条路线。同一交付和证据只登记一次，引用到所有适用条款。下表表示工作包归属，原专项阶段只有其全部要求满足后才可关闭，不能凭映射自动关闭。

已确认的细化采用以下契约：面板几何与动画以 03 为准，紧凑基准 600×38 DIP，展开基准 920×560 DIP；MCP 工具以 05 八项加 06 的 workbench_record_repair 为统一集合；修复和工作树上下文以 06 及本总纲补充规则为准。02 的旧尺寸和六工具表只保留历史定位价值。发现其他不相容要求时记录具体冲突，停止受影响工作并确认取舍。

最终结束要求包括原 D07 全部必需项、FX 实际观感确认、04/05 的组合与接入验收、06 的 P01—P16，以及本文件新增验收。未验证的能力保留待验，不用手动试跑成功替代自动连接或真实桌面证据。

## 3. 站点修复支线与轮次

每个主站点展示正常子步骤与修复支线。修复按 RepairCase 分组，各 RepairAttempt 按追加顺序展示。示例：

```text
U05 插件与核验闭环［待核验］
 ├─ R01 来源绑定错误［处理中，已执行 2 轮］
 │   ├─ A01 第 1 轮 → 失败 → 证据 E01
 │   └─ A02 第 2 轮 → 待核验 → 证据 E02
 └─ R02 回执遗漏［已解决，1 轮］
     └─ A01 第 1 轮 → 核验通过 → 证据 E03
回归位置：U05 原验收条件，满足后重新检查 U06/U07 前置
```

首次原定交付不计修复轮次。一次明确登记并实际开始的修复尝试计一轮，可跨多个聊天轮次；重发工具、重试同一请求及切换聊天不加轮数。新方法或下一次明确修复执行建立新 attemptId/executionId。取消、中断的已开始尝试计入执行轮次并单列结果；未开始的计划尝试不计。每案例显示总轮数、失败/中断/待核验数；主站汇总全部案例的尝试数，同时展示未解决案例数，避免混淆。

修复支线不增加主路线站数，不改变验收完成比例分母。解决案例不自动完成主站。案例重新打开保留原轮次并追加尝试。合并重复案例保留原 ID 和计数出处，避免重复累计。每轮记录目标、原验收项、方法、修改、版本/内容指纹、证据、剩余差距及回归锚点。

## 4. 防偏离补充契约

- 跟踪缺口：可观察到活动却没有业务登记或结束回执时，显示待补齐；不可观察则显示覆盖未知。人工补录保留录入时间与实际发生时间、来源可信等级。下一次执行先核对缺口。
- 停滞判断：按同一验收项比较每轮差距。初始建议连续两轮结束仍未缩小差距时提示重新评估，阈值在项目建立时确认。轮数本身不证明失败，不能自动停止宿主或降低标准。用户决定继续原方法、换方法、受控拆分、等待外部条件或提出方案变更，并记录理由。
- 站内细化：子步骤必须关联父站目标和验收项。只是实现细化时保留主路线；改变交付、依赖或验收的内容进入方案修订。新增范围不能混入必要修复。
- 并行认领：记录当前执行、负责聊天、工作树、允许并行范围及接手记录。同一工作树冲突修改先处理归属。接手后旧执行的迟到结果只进入历史/待核对，不能覆盖新交付。业务认领不声称能阻止外部 Git 或文件操作。
- 需求覆盖：为原始需求设置稳定 ID，关联站点、条件和证据；发布与项目结束均列出未覆盖项。用户核对语义覆盖，AI 提交映射候选。需求调整保留初始版本及批准记录。
- 回归界面：主窗口同时显示原定目标、当前修复、剩余差距、回归位置和等待对象；顶部提供修复轮次摘要和详情入口。获取续接上下文时包含当前 revision，开始前重新核对。

## 5. 手动试跑准备

手动派发和手动登记可立即验证流程。首次试跑先完成 U01，之后逐站派发；只有前置有效通过才启动下一站。可以在现有工作台录入已支持的字段，尚无修复支线功能时用 Markdown 台账补充，明确唯一权威位置。新版本测试使用数据副本，避免正在开发的工作台破坏自身执行记录。

开始前准备以下六项：

1. 固定基线：仓库、分支、HEAD、六方案及本总纲的提交版本、工作区现状。
2. 主台账：U01—U08、前置、状态、负责聊天、工作树、最新回执、证据及下一步。初始状态全部待执行。
3. 站点卡：目标、范围、交付物、逐项验收、前置、退出条件和回归位置。
4. 修复台账：案例、轮次、方法、结果、剩余差距、版本和证据，采用第 3 节规则。
5. 证据目录与核验安排：区分执行自述、实际检查、独立核验和用户观感；规定谁核验哪些条件。
6. 备份与会话交接：台账纳入 Git；真实聊天、凭据和大型产物不入库，证据索引记录位置及哈希；换聊天复制最新站点卡和未决修复。

首次实际执行时在本主题的 02_执行过程 创建主台账和站点记录，使用实际日期；本次文档整理不预填执行结果。原通用指令模板继续复用，方案总步骤填 U01—U08，共八步，专项编号作为来源引用。每次只派发一个站点或明确修复尝试，消息发送和记录均由用户主动完成。

### 手动派发内容

```text
方案：本总纲及本站引用章节，填写准确版本
本站：Uxx，当前 revision/台账版本
原始目标及本站验收：逐项列出
现场：仓库、分支、工作树、HEAD、聊天
前置证据：逐项列出
本次范围：首次交付 / Rxx 的第 n 轮修复
本轮差距、方法及结束条件：填写
回归位置：原站点及需重新检查的依赖
要求：先核对现场，按范围执行，提交实际结果与证据；新范围单列
结束回执：完成内容、条件结果、版本、阻塞、剩余问题、回归位置、下一步依据
```

执行后先登记实际结束，再核验条件；未通过则在原站建立/追加修复。通过后核对所有后继前置，由用户发送下一次指令。长时间等待记录等待对象和恢复条件。手动录入标记 manual，不能标为 hostObserved 或宣称 MCP 已接入。

## 6. 新增必需验收

| 编号 | 场景 | 通过条件 |
|---|---|---|
| G01 | 漏开始、漏回执、不调用 Skill、取消 | 显示真实跟踪缺口，补录可追溯，不伪造完成 |
| G02 | 两次无进展后再次修复 | 支线轮数准确、出现重新评估记录、原标准保留 |
| G03 | 同请求重试、跨聊天、取消、案例重开 | 不重复计轮，保留中断及完整历史 |
| G04 | 粗站细化及额外优化 | 子步骤有归属，新范围经确认，主路线分母正确 |
| G05 | 双聊冲突、接手后旧回执迟到 | 明确归属，旧结果不能覆盖当前执行 |
| G06 | 原需求遗漏但登记站点全通过 | 项目不能被声明目标全部达成，显示覆盖缺口 |
| G07 | 查看修复与下一步 | 用户无需翻聊天即可找到原目标、差距、轮数及回归位置 |
| G08 | 真实组合任务 | 两线并行、多轮失败、换聊天、新范围、停滞调整、回归、合流失败再修复、最终验收均有证据 |

手动试跑评价流程是否可理解、记录是否可持续、下一步是否有全局依据。自动化产品评价真实工具往返、遗漏处理、数据一致性和原生体验。两类结果分别记录。
