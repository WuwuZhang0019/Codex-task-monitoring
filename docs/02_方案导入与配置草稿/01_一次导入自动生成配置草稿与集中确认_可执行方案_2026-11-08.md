## 1. 问题、目标与独立范围

当前用户导入方案后，仍需在“管理任务与方案版本”逐个配置文件夹、任务、来源、方案版本、站点和依赖，配置成本高。现有AI提取只能产生旧路线steps，不能形成完整新版监测模型。

## 3. 用户操作流程

1. 点击“导入执行方案”，上传UTF-8 Markdown/文本或粘贴原文。首期沿用文本入口，不新增PDF/OCR、任意路径读取或远程抓取。
2. 系统读取一次原文，保留不可变内容摘要和上传文件名；向用户说明发送至所配置模型的文本范围。点击“生成配置草稿”后才调用模型；未配置或请求失败可重试或转手动，不静默伪造草稿。
3. 显示同一集中确认页：项目与方案、任务/文件夹映射、路线图、待补信息。已提取内容默认展开摘要，用户只改错项和缺项，不重新填写全部字段。
4. 对原文中没有的外部项目标识、聊天、仓库、工作树、分支、HEAD等，显示“待绑定/待核实”，不让这些未知项全部变成首次保存的必填表单。仍允许保存为未绑定配置；执行/回执匹配边界沿用既有规则。
5. 缺项目/任务目标、任务归属、站点范围/验收、依赖冲突或方案版本等关键问题，集中列出并定位。用户可修正并重校验，或保留草稿退出；不能将不可用草稿显示为“已配置”。
6. 用户点击一次“确认并创建项目”，服务端校验并原子发布；页面进入新版监测图。默认站点未开始，无回执、核验、实际开始或关闭记录。按钮不声称“已发送”或“已执行”。

本期默认新建项目。对已有项目只提供“另建项目导入”，不覆盖其原文、身份或历史；已有空项目的直接应用和既有路线版本升级不在首期纳入，避免暗中改写基线。

## 4. 自动生成与人工确认的边界

| 内容 | 自动生成规则 | 需确认或缺失处理 |
|---|---|---|
| 项目名称、目标、项目验收 | 从原文提取并附原文位置 | 无出处时集中补齐，不用任务验收冒充项目最终条件 |
| 方案原文/摘要/日期/版本/章节 | 原文服务端保存，内容SHA256绑定草稿；上传文件名作来源标签 | 浏览器不能得知完整本机路径，不拼造；来源路径可待核实；方案日期/版本未知时让用户确认实际值 |
| 任务线与终点 | 按明确任务边界和交付条件提取 | 不把每个章节或每站当成独立任务；多任务归属不明确时阻止正式发布 |
| 文件夹 | 原文明示则生成本地文件夹实体；单任务无明确名称时给可编辑本地容器名 | 外部Codex项目ID不生成；明确标“本地暂定容器”，由用户集中确认任务映射 |
| 聊天、仓库、分支、HEAD | 只采纳原文或用户输入并标来源快照 | 本地实体ID与外部聊天标识分开；不创建假聊天来满足可开始条件 |
| 站点ID/编号 | 原文明示编号保留；服务端生成稳定本地UUID；缺编号时生成本地编号并提示 | 重号需结合任务定位；重试/确认不能重新分配同一草稿实体身份 |
| 前置、后继与交接 | 仅采纳明确依赖；合法后继由确认后的依赖图一致生成 | 不从文字顺序猜依赖；含糊边、缺失引用、自环/循环集中处理；跨线合流检查全部前置 |
| 验收、状态与历史 | 验收引用原文；状态由既有监测规则计算 | 无验收仅作草稿待补；不自动判通过、不继承文档“已完成”作为有效证据 |
| 额外优化/暂停 | 原文明示本期外事项进入candidates，并保留暂停 | 不进入必需任务/站点或依赖，不能阻塞本期关闭；不能擅自移出原方案必需工作 |

方案步骤总数与顺序另存为草稿中的“原文路线声明”，带出处与完整性判断；用户集中核对完整清单。不得把已提取站点数直接标为原方案总数。首期不改变outputs现有保守判断规则；不可识别的完整路线继续显示待核实。

## 5. 草稿契约与服务边界

新增独立导入服务，建议文件`app/server/import-drafts.mjs`和前端`ImportWizard.tsx`，不把复杂流程堆入main.tsx。I01冻结以下语义，再确定具体类型：

- Draft：id、schemaVersion、revision、创建/更新时间、status（draft/needs-review/ready/committed）、source（原文、SHA256、名称、可选真实路径）、候选project/model、provenance、issues、确认摘要、提交结果引用。
- provenance：字段路径、原文逐字摘录、段落/字符位置、来源类型（原文/用户填写/系统ID）；摘录必须出现在原文，不把模型置信分当作事实。
- issues：稳定编号、字段/实体引用、缺失或冲突原因、blocking标记及可执行修正方式。非阻塞外部身份缺失与无法发布的业务结构问题分开。
- 草稿不含receiptLog、lifecycle、关闭/核验通过状态。服务端拒绝客户端夹带这些受保护字段，而不是只靠前端隐藏。

建议API（均受现有本机Host/Origin与请求体限制）：

| API | 行为与边界 |
|---|---|
| `POST /api/import-drafts` | 接收原文与来源标签，显式触发提取；返回草稿及校验问题，不修改已有项目 |
| `GET /api/import-drafts/:id` | 读取草稿与revision；支持刷新恢复 |
| `PUT /api/import-drafts/:id` | 提交集中修正；校验revision，不接受静默覆盖 |
| `POST /api/import-drafts/:id/commit` | 携带expectedRevision、sourceHash和确认摘要；只在无阻塞问题时发布，返回projectId及模型revision |

重试失败、模型截断/非法JSON/出处不符、超过现有限额或网络超时均展示具体可恢复提示；不吞错误、不自动截断方案、不在失败时创建半配置项目。内容限制与ai.mjs/validation.mjs现有限额对齐，端到端请求不得超过2MB；不借新功能宣称已解决旧ECONNRESET。

## 6. 保存、幂等和恢复

这是实现前必须解决的关键问题：现有projects与models分文件，各自原子写，不等于共同原子提交。禁止简单前端顺序调用“创建项目→保存模型”并宣称一次成功。

建议在现有串行写入体系增加导入发布协调器：先生成服务端稳定projectId和实体ID，将待发布项目/模型及确认摘要写入隔离staging；采用持久化事务记录（prepared/committed）和读取可见性门禁。只有两个有效文件均准备就绪并写入提交标志后，项目列表和详情才对外可见。启动时恢复未完成事务：按同一输入/摘要完成发布或保持不可见并报告恢复失败，不能创建空替代数据。恢复规则及备份范围在I01定稿、I03通过故障注入验收后才可接入界面。

同一draft确认重复提交返回同一projectId，不新增项目、任务或历史。不同确认摘要/旧revision拒绝409，提示重读；并发双击和响应丢失后重试同样幂等。用户修改原文后创建新草稿版本，不把旧模型配到新原文。

草稿刷新/服务重启后可恢复；用户可显式放弃未发布草稿，不删除已发布项目。保存、备份及故障恢复文档需涵盖drafts/staging/事务记录，不能只备份projects.json。实施不自动迁移或试写真实用户目录。

每项记录输入、操作、预期/实际、证据位置、精确版本及限制。优先复用未受影响的既有证据；领域测试不足以替代真实界面/HTTP/磁盘组合验证。

| 场景 | 必须看到的结果／证据 |
|---|---|
| 单线完整方案 | 上传一次→草稿自动产生全部必要实体→一页确认→直接进入新版监测；无需逐项添加站点/ID/依赖 |
| 四线与集成、两线合流 | 任务边界、唯一文件夹及全部依赖来自明确原文；不生成重复联调任务 |
| 外部身份缺失 | 明示待绑定，允许保存合法本地配置；不冒充真实Codex项目或聊天，不自动亮绿 |
| 目标/验收缺失与依赖含糊 | 问题集中可定位；阻塞问题未修复不发布；用户修正有记录与来源，不编造通过 |
| 非法提取 | 原文不存在的摘录、未知字段、重号/缺引用/循环、非法JSON、超限/超时均拒绝或待修正；无半项目 |
| 原文含命令或密钥请求 | 仅作为不可信资料；不执行、不访问其URL，不泄露系统提示或本地凭据 |
| 两次确认、并发、响应丢失重试 | 同一draft仅一个projectId，旧revision/新内容冲突明确409，不重复创建 |
| 取消和刷新/冷重开 | 取消未发布不改正式项目；保存草稿可恢复；状态及待补信息一致 |
| 跨文件故障恢复 | staging、项目、模型、提交标志各阶段注入失败；未提交不可见，恢复后完整且幂等，原项目不受损 |
| 导入已有“已完成”文档 | 全站未开始/待核验，无独立验收或关闭历史，不按文本自述自动完成 |
| 已有项目与修订版本 | 首期明确另建项目导入；原身份、原文、核验、关闭及数据不被覆盖 |
| 本期外优化/暂停 | 只做独立候选，暂停不恢复；不误移除原方案必需项 |
| 最少补录与集中确认 | 用完整单线及多线样例观察：不手填稳定ID、不重复录入已明示字段；所有缺项同页展示，确认后一次发布 |
