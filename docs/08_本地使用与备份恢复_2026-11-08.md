## 2. 先分清项目、文件夹、任务与聊天

| 对象 | 应填写及使用的身份 |
|---|---|
| 开发项目 | 本地项目 UUID；容纳方案、多个文件夹和多条任务线，另有项目最终验收 |
| Codex 项目文件夹 | 名称和外部项目标识分开登记；不是磁盘目录，也不是 Git 分支 |
| 任务线 | 固定归属一个文件夹；有原始/当前目标和终点条件；可以跨多个聊天 |
| 站点 | 所属任务、稳定 ID/编号、方案版本/章节、目标范围、验收及全部依赖 |
| 聊天来源 | 关联既有任务，登记聊天标识、仓库、工作树、分支、HEAD、回执位置及时间 |

换聊天时添加来源并继续引用原任务/站点，不重建路线。文件夹同名或回执编号相同不能代替身份核对。未接入 Codex，外部标识需要操作者填写；未知写待绑定/待核实，不能编造。

## 3. 创建项目并固定方案

1. 点击“新建项目”，填写名称和目标。旧方案导入仍可用；“原始手动记录”的完成状态仅保留自述。
2. 打开“管理任务与方案版本”。空项目有一个默认任务，可直接编辑该任务。添加文件夹，给任务选择唯一归属，填写当前目标、按初始方案确认的原始目标、终点验收和交接对象。任务已有文件夹及原始目标保存后不能覆盖。
3. 添加方案版本，填写版本号、实际日期、完整来源路径、章节、原文、目标和项目验收。首次设置初始/当前方案；保存后的版本原文不能修改，新修订应追加版本。登记来源路径不会自动读取文件，应将实际原文复制到“方案原文”，并自行核对路径与内容。
4. 添加聊天来源，选择既有任务；同一任务可添加多个聊天。分支和 HEAD 是登记快照，执行前需要重新检查现场。
5. 添加或核对站点，按原方案填写编号、范围及逐项验收。前置/后继用稳定 ID，每行一个，界面提供编号到 ID 的映射。依赖和对应后继应成对登记；合流列出所有必要前置，不能只填最近的一条线。
6. 点击“保存任务关系”。出现版本冲突时重新读取并对照自己的修改，不能用旧内容覆盖新状态。左栏站点数和底部原始路线属于旧导入模型，新版实际状态以“核验监测与自动收敛”为准。

方案总步数与圈号来自已登记方案原文中能明确识别的完整路线，不从站点数量或 M06 的数字猜测。当前支持本项目原方案第 10 节的完整路线表，或下列明确独立章节（连续编号、稳定步骤号、每步一行）：

```text
## 完整方案步骤
1. S01：实现原定功能
2. S02：完成原定验收
```

操作者仍须对照原文件确认登记原文真实完整。其他格式、重复/冲突章节或不能确定的顺序会明确待核实，并把登记站点仅作为定位清单；不会将子集冒充完整方案。无需为了取得圈号擅自改写原方案或批准范围变更。

## 4. 从回执到核验，再到开始、交接和关闭

1. 打开“回执与头尾核验”，选站点生成 JSON 模板。填写真实身份引用、精确 `deliveryVersion`、完整原文 `raw`、实际交付 `actual`、必要阻塞和 `next` 中实际提出的后继目标/范围/交付。可粘贴或读取 JSON 文件。导入只登记自述，即使 checks 写通过也不自动亮红灯。
2. 选历史回执，填写核验人、实际检查方法及适用范围。逐项读交付物、报告或实际界面，对照版本和预期，填写结果及判断理由；证据填写位置、交付版本、检查方法和可用性依据。只有实际检查后才选“我已按记录的方法检查，证据有效”。未检查、打不开或版本不符保留待核验。
3. 分别核验本站、任务终点和项目最终条件。对原始任务/项目目标的对照项不能省略。比较每条后继的目标、范围和交付，说明为什么相同或不同；编号相同不足以通过，措辞不同可以有明确依据地匹配。
4. 保存独立核验后查看监测结果。红色表示验收通过；绿色表示已有实际开始证据；暗色同时带“等待依赖／待核验／可开始”等文字。可开始不等于已经开始。
5. 实际开始后选择监测站点，选正确聊天、填实际开始消息或执行记录位置，点击“登记实际开始”。这只是登记来源，不发送指令、不启动任务。前置不齐或任务有效关闭时不能登记。
6. 达到任务既定终点后自动关闭，显示原目标、实际交付、验收、最初预期及偏差/交接。开发任务可独立结束，由集成任务接手；项目必须另有全部任务及项目级有效证据才能结束。

工作台保存的是操作者的证据判断，不自动认证任意文件/URL、核验人账号或真实工程结果，也不访问证据路径、调用 AI 替代审签。必须写实际检查方法及理由，不能只填写路径、提交号或“已完成”。同一回执重复导入不会再次推进或增加事件；不同来源和更正内容追加历史。

证据撤回时在回执界面填写失效原因并标记该核验失效；重验追加新记录。方案修订先明确影响并追加版本，保留初始原文、目标及旧验收。历史已关闭但当前证据不适用时显示待复核，不继续输出虚假任务/项目结束；缺旧站点快照明确待核验，不重建历史。

## 5. 预览和复制

| 结论 | 可复制内容 |
|---|---|
| A | 留在本站，仅修失败项 |
| B | 留在本站，仅补必要核验 |
| C | 等待对象、全部依赖及恢复条件，无执行指令 |
| D | 原方案合法下一站的执行指令；分叉可逐边选择 |
| E | 本任务交付结束及交接对象，无本任务下一步 |
| F | 项目最终结束，无下一步 |
| G | 方案冲突、差异及待决定事项，无擅自执行指令 |

“核对提示词”只请求路线核对和生成；“执行指令”才用于实际本站工作。确认站点、来源、方案及结论后再复制。E/F 固定包含“本任务无下一步执行指令，到此结束”。

预览变化后点击“重新生成输出”。每次复制先重新核对状态；对象、方案或证据变化会拒绝过期内容并要求重生。剪贴板失败有明确反馈，可检查浏览器权限或手动选择当前预览。“已复制”始终伴随“尚未发送”，不会显示已发送或自动变成进行中。

额外优化、未来需求和已暂停专项，在关系管理底部“额外优化与暂停专项”独立登记名称、原因、日期和候选/暂停状态。它们不进入本期站点或依赖，也不阻塞关闭；刷新和重开不会自动恢复暂停执行。独立实施需另有方案和授权。

## 6. 配置与数据位置

默认数据目录：`G:\rust\Codex-task-monitoring\app\data`。需要另选目录时在**启动前**设置绝对路径：

```powershell
$env:WORKBENCH_DATA_DIR = 'G:\rust\Codex-task-monitoring-local-data'
node app/server/index.mjs
```

同名系统环境变量优先于 `app/.env`。可将 `app/.env.example` 复制为 `app/.env`，填写自选兼容服务的 `OPENAI_BASE_URL`、实际 `OPENAI_MODEL` 和 `OPENAI_API_KEY` 后重启。AI 只用于可选方案提取/总结，会向该服务发送相应文本；本次验收未调用模型，也不需要密钥。`.env` 和数据不入 Git。

| 文件 | 作用 |
|---|---|
| `projects.json`、`projects.json.bak` | 原项目/导入路线与上一版备份 |
| `models/<项目UUID>.json`、对应 `.json.bak` | 方案、关系、回执、独立核验、开始/关闭/待复核历史和候选 |
| `models/<项目UUID>.json.legacy.json` | 首次迁移的原始项目快照，不能删除冲突快照来强行迁移 |

旧数据不自动升级为有效验收；读取旧项目不会自行批准状态。界面的“导出项目”只导出旧项目模型，不包含全部新版关系与核验历史，**不能代替整目录备份**。

## 7. 停止服务后备份和恢复

先在服务窗口按 `Ctrl+C`，确认服务进程已退出，再复制整个实际数据目录。不要在持续写入时拼接不同版本的主文件和备份。下例为操作者自行执行的路径示例；本次验收仅在隔离目录验证，不曾复制真实数据。

```powershell
$workbenchData = 'G:\rust\Codex-task-monitoring\app\data'
$workbenchBackup = 'G:\backup\Codex-task-monitoring\2026-11-08'
if (Test-Path -LiteralPath $workbenchBackup) { throw '备份目标已存在，请另选新目录' }
New-Item -ItemType Directory -Path (Split-Path -Parent $workbenchBackup) -Force | Out-Null
Copy-Item -LiteralPath $workbenchData -Destination $workbenchBackup -Recurse
Get-ChildItem -LiteralPath $workbenchBackup -Recurse -File
```

恢复优先复制到一个不存在的新目录，保留现有数据以便对照：

```powershell
$workbenchRestored = 'G:\rust\Codex-task-monitoring-restored\2026-11-08'
if (Test-Path -LiteralPath $workbenchRestored) { throw '恢复目标已存在，请另选新目录' }
New-Item -ItemType Directory -Path (Split-Path -Parent $workbenchRestored) -Force | Out-Null
Copy-Item -LiteralPath $workbenchBackup -Destination $workbenchRestored -Recurse
$env:WORKBENCH_DATA_DIR = $workbenchRestored
node app/server/index.mjs
```

重开页面，逐项目核对方案版本、任务/站点、来源、回执、证据及关闭/待复核历史，再决定是否作为工作目录。M06 已停止服务、复制完整隔离数据、恢复到另一目录，并逐字段对照所有项目的 model、receipts、monitor、outputs 四接口，真实界面同时核对关闭与待复核状态。

损坏或缺主文件但存在 `.bak` 时服务不会清空重建。先保留全目录副本，在恢复副本中确认有效备份及其时间，再把相应 `.bak` 复制为原主文件名并启动核对；不要覆盖原始目录或混用不同批次。该单文件救援沿用 M02 存储证据，M06 新增实测的是完整目录恢复。

## 8. 开发、复验与限制

开发依赖来自 `app/package-lock.json`：在 app 目录运行 `npm ci`，然后 `npm run dev`；开发 Vite 通常在 4317，后端 4318。改源码后运行 `npm run build` 同步 dist；生产启动不会自动构建。

M06 可复跑入口（app 目录）：

```powershell
npx playwright install chromium --only-shell
node tests/m06.e2e.mjs
node tests/m06-start.e2e.mjs
```

启动专项要求 4318 空闲；它将当前 server、dist 及通用模板复制到不含 `.env` 的隔离目录运行，保留操作者原配置，不需要删除或重命名 `.env`，只停止自身启动的进程。场景测试禁用 AI，使用独立数据，证据写 `app/test-results/m06`，不进入 Git。Windows 若浏览器安装在用户缓存而执行环境缓存不同，可按实际位置设置 `PLAYWRIGHT_BROWSERS_PATH`；受限执行环境还须允许本机回环访问及隔离目录原子重命名，不能通过破坏正确存储逻辑绕过限制。

本期未接入 Codex 自动采集、指令注入和自动执行，也不验证 PDSD 真实集成。外部方案格式无法核定总数、缺身份或历史快照时保留待核实。既有超过 2MB 请求体场景曾偶发 ECONNRESET，根因仍未确认；本次标准业务场景未触及该上限，不能宣称该偶发问题已经解决。
