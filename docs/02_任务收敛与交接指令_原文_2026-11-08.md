# 任务收敛与交接指令（原文）

日期：2026-11-08  
状态：已归档，可复制使用

下方代码块完整保留本次对话上一条回复中的提示词，不作改写。文档标题、日期和本说明不属于提示词。适用背景与实施方案见 [可执行方案](01_Codex任务状态监测工作台_可执行方案_2026-11-08.md)。

```text
请依据既定可执行方案，核对当前任务的完成位置，并输出可复制到新会话执行的任务指令，或者输出任务结束回执。

日期：填写生成当天日期，格式 YYYY-MM-DD。

一、先核对依据

先读取：
G:\rust\PDSD-v0.3\docs-v0.4.0\03_功能新增\05_Agent工作台\03_四条开发线状态确认与集成条件_2026-11-06.md
以及其中引用的权威方案。

核对当前仓库、Git 分支、工作树、代码、交接记录及验证证据。
文档是指定日期的状态快照；如与当前事实不一致，明确差异，以可核实证据判断实际状态。
本次请求仅核对和生成指令，不执行新的开发、合并或方案修改。

二、先确定终点，再决定有没有下一步

明确区分：
1. 本站步骤的目标与完成条件。
2. 当前任务线的目标与完成条件。
3. 项目的最终目标与完成条件。

任务线达到交付条件后即可结束；项目尚未完成，不代表本任务线必须继续开发。
需要由集成线或其他任务接手的工作，应登记交接对象，不追加成本任务线的新步骤。

不得因为要求输出报告，就强行生成下一步。
不得将可选优化、新需求、已暂缓事项自动加入本期路线。
不得通过降低验收标准、删除未完成项或改写原目标来宣布完成。

三、核对本站的头和尾

本站的头：
- 所属任务线、步骤编号和名称。
- 方案出处及版本；没有版本号时记录文档日期和章节。
- 任务目标。
- 前置条件。
- 明确、可验证的完成条件。

本站的尾：
- 实际完成内容。
- 交付物、相关提交及验证证据。
- 每项完成条件：通过 / 未通过 / 待核验。
- 未解决事项是否阻塞本站完成，以及依据。
- 是否达到本站原定目标。

“已编写”“已提交”“已有交接说明”不能直接等同于验收通过。
缺少证据时标为待核验，不得推断为完成。
已通过且未受本次改动影响的验证，不重复安排。

四、下一步必须来自既定路线

只有本站已满足完成条件，才判断能否进入方案中的下一站。

必须核对：
- 本站尾部提出的下一步编号、目标和交付内容；
- 原方案下一站头部规定的编号、目标和交付内容；
- 下一站所需的全部前置条件，包括其他任务线的依赖。

编号、工作范围、交付要求必须一致，不要求措辞逐字一致。

如果本站未通过：
仍停留在本站。只列满足原验收条件所必需的修复或核验，不伪装成推进到下一站。

如果下一站的依赖未满足：
标记等待依赖，说明等待谁、等待什么，不生成无关替代工作。

如果建议的下一步不在原方案内，或必须改变原有目标：
标记方案变更待确认，说明原因和影响，不自行扩展路线。
没有稳定步骤编号时，可以按原方案建立对应编号，但不得借此新增步骤。

五、明确选择一个结论

结论只能为以下之一：

A. 本站未完成：继续本站必要工作。
B. 本站待核验：证据不足，先补齐必要核验。
C. 本站已完成，等待依赖：暂不进入下一站。
D. 本站已完成，可进入既定下一站。
E. 本任务线已完成，交付其他任务线接手。
F. 项目最终目标已完成。
G. 方案存在冲突或需要变更：等待明确决定。

选择 E 或 F 时：
明确写“本任务无下一步执行指令，到此结束”。
可以列明其他任务线的交接事项或独立后续建议，但不得将它们写成本任务继续执行的要求。

六、固定输出格式

【路线核对】
- 日期：
- 开发项目：
- 所属 Codex 项目文件夹：
- 任务线名称：
- 仓库 / 工作树 / Git 分支：
- 方案依据及版本：
- 任务线最终目标：
- 当前步骤编号及名称：
- 本站验收结果：
- 本任务线剩余的既定步骤：
- 与最初方案的差异：
- 结论：A / B / C / D / E / F / G
- 判断依据：

如果部分信息无法确认，明确写“待核实”，不得猜测。
“剩余步骤”必须来自原方案；无法核定时说明原因，不编造剩余数量。

【可复制执行指令】
仅在 A、B、D 情况下生成，并置于一个完整文本代码块中：

1. 任务名称：沿用任务线和步骤编号，说明是继续本站、核验本站还是进入下一站。
2. 执行环境：仓库、工作树、分支及所属项目文件夹；执行前重新核对。
3. 方案依据：文档位置、版本及对应章节。
4. 本站目标：明确本次必须达到的结果。
5. 范围边界：必须完成什么，哪些内容不属于本站。
6. 前置条件：上一站的交付结果、验证证据及其他必要依赖。
7. 执行步骤：仅包含到达本站目标所必需的工作，优先复用已有实现。
8. 验收条件：逐项列出检查方法、预期结果和需保留的证据。
9. Git 提交：按可验证阶段提交；提交前检查范围，不包含无关改动。
10. 停止条件：验收条件全部满足后，停止扩展本站工作；若遇到阻塞，准确记录，不用额外工作掩盖阻塞。
11. 完成回执：按下方格式输出。完成本指令后仅报告交接状态，不自动执行下一站。

【执行完成后必须返回的回执】
- 日期：
- 任务线 / 步骤编号：
- 本站原定目标：
- 实际交付：
- 提交及验证证据：
- 各项验收条件及结果：
- 本站是否完成：是 / 否 / 待核验
- 是否满足最初方案预期：满足 / 不满足 / 待核验
- 当前阻塞：
- 任务线是否已到终点：
- 下一站：原方案编号及目标 / 无
- 本站尾部与下一站头部是否匹配：匹配 / 不匹配 / 待核验 / 不适用
- 下一站全部前置条件是否满足：
- 交接对象：本任务线 / 其他任务线名称 / 无
- 结束结论：继续本站 / 等待核验 / 等待依赖 / 可进入下一站 / 本任务线结束 / 项目结束 / 方案变更待确认

对于 C、E、F、G：
输出等待、交付或结束回执，说明依据及恢复条件（如适用），不要生成虚假的下一步执行指令。

确保生成的指令脱离当前聊天也能独立理解和执行。
不得虚构项目现状、扩大任务范围，或将未经验证的工作报告为已完成。
```
