## 使用流程和信任边界

1. 先在“管理任务与方案版本”保存项目关系，明确任务、文件夹、聊天来源、站点方案和验收条件。未绑定或归属错误的回执保留在隔离列表，不能核验推进。
2. 打开“回执与头尾核验”，选择站点生成结构化回执模板。将完整原文放在 raw，填写实际交付 actual、精确 deliveryVersion 和真实身份引用；checks 只是执行方报告。可粘贴 JSON 或读取 JSON 文件。next 中的目标、范围和交付应来自实际回执，不自动填成与后继一致。
3. 导入后只登记来源自述，不视为通过。选择历史回执，填写核验人、实际检查方法、逐项结果和判断依据；登记证据位置、适用交付版本、实际检查方法、可用性依据和有效/无效/待核验。
4. 查看本站尾部与各后继头部对照，明确匹配、不匹配或待核验，并说明目标、范围、交付要求的比较依据。措辞可以不同；编号相同本身不构成通过。
5. 保存独立核验，查看 A—G 结论、逐项结果、等待对象及交接边判断。任务终点和项目完成条件单独核验；初始方案验收及原始目标不能被新版条件遮盖。
6. 证据撤回或发现核验错误时，填写原因并追加失效记录；重新核验追加新记录。旧回执、旧核验及原时间保留。

本版的证据可用性与语义比较采用显式人工核验：操作者实际检查后登记方法、结果与理由。它不是文件或 URL 的自动真实性认证，也不认证填写姓名的账号身份。不自动读取任意证据路径、访问外链或请求模型。未实际检查应保留待核验，不能把路径字符串、Git 提交或回执里的“完成”当作证明。

## 结构化数据和持久化接口

`GET /api/projects/:UUID/receipts` 返回当前关系 revision、规则版本、站点结果、隔离回执及完整日志。`POST` 使用当前 revision，操作为 import、review、invalidate；旧版本写入拒绝为 409。请求仍受本地 HTTP 和体积校验约束。

import 的 receipt 包含 projectId、folderId、taskId、stationId、planId、sourceId（已登记聊天来源的稳定 ID）、deliveryVersion、raw、actual、blockers、checks、next。checks 为 criterion/result；next 为 stationId/goal/scope/delivery，分叉逐条记录。blockers 只记录阻塞交付的必要未决项，非必要优化不应填入该数组。

review 含 receiptId 和独立 review：reviewer、method、checks、taskChecks、projectChecks、evidence、handoffs。每个验收项使用方案原有 criterion，result 为 passed/failed/pending，附 reason 和 evidenceIds。每份证据含 id、location、deliveryVersion、method、reason、result（valid/invalid/pending）。每条 handoff 含 stationId、result（matched/mismatch/pending）、reason。默认均待核验；缺字段、未知枚举和重复验收项会拒绝。初始目标单列为 `原始目标：<初始方案目标>`，与初始/当前方案验收及项目条件共同核对。

invalidate 使用 reviewId 和 reason，追加失效原因及服务端时间。回执内容按规范化摘要去重；相同内容重复导入不增加 revision 或状态事件。相同的最近核验重复提交也幂等，纠正判断或失效后复核会新增记录。收到不同聊天来源或新内容时追加回执，不覆盖历史。

日志保存于 M02 项目关系文件中的 receiptLog，含 receipts、reviews、invalidations、events。普通关系 PUT 无权替换或删除该日志。核验记录包含规则版本、服务端时间、当时站点头及适用方案摘要；读取时重新计算当前适用性。本站、后继头、方案或相关来源改变后待复核，无关聊天增加不影响原核验。证据交付版本必须与回执精确对应。存储仍使用 M02 的备份及失败恢复机制。

## 判断规则

| 结论 | 本站规则 |
|---|---|
| A | 逐项验收失败、终点验收失败或有阻塞交付事项，继续本站必要工作 |
| B | 无有效回执、缺证据/核验、证据失效或版本不适用、头尾信息不充分，等待必要核验 |
| C | 本站逐项核验通过，但前置或后继仍有未满足的依赖，列出等待站点 |
| D | 本站有效通过、对应边的头尾匹配和后继全部前置满足，只表示可开始 |
| E | 任务全部站点与任务终点条件有有效证据，交付其他任务；项目条件另行核对 |
| F | 所有必要任务与项目、初始方案及原始目标的预设条件均有对应证据 |
| G | 实际尾部范围不匹配或提出非法后继，停止路线推进并明确差异 |

结果分别保留 localPassed（本站逐项验收）与 passed（含全部前置及对应交接边）。依赖递归核对全部祖先；合流不能因一条分支已完成就解锁。没有 matched 的必要交接边不作为有效前置。任务可在向其他任务交付后独立结束，不复制接手任务。这里输出 E/F 资格判断，实际任务/项目关闭和红绿暗渲染属于 M04，没有在 M03 自动关闭或生成执行开始事件。
