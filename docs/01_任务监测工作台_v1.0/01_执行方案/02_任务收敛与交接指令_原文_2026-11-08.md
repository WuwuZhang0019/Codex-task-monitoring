# 任务收敛与交接指令（原文）

## 通用模板

复制本节代码块后，将所有 `【需填写：……】` 替换为实际信息。方案路径是必填项；项目、任务线和当前站点若尚不清楚，可保留“待核实”，由执行会话核对，禁止猜测。方案引用其他权威文件时一并读取；多个方案有冲突时说明冲突。仓库、工作树和分支以现场核对结果为准。日期由执行会话填写当天日期。

```text
请依据既定可执行方案，核对当前任务的完成位置，并输出可复制到新会话执行的任务指令，或者输出任务结束回执。本次只做核对和生成，不执行新的开发、合并或方案修改。

【项目资料：使用前按实际情况修改】
- 可执行方案路径（必填）：【需填写：完整路径】
- 其他权威方案或交接资料路径：【需填写：完整路径；没有则写无】
- 开发项目：【需填写：项目名称，未知写待核实】
- 所属 Codex 项目文件夹：【需填写：文件夹名称或标识，未知写待核实】
- 任务线及当前站点：【需填写：名称、编号；未知写待核实】
- 仓库、工作树及 Git 分支：【需填写：已知信息；未知写待核实，执行前重新核对】
- 日期：填写生成当天日期，格式 YYYY-MM-DD。

一、核对依据和目标

读取上述方案及其引用的权威资料，核对当前仓库、分支、工作树、代码、聊天交接记录、交付物和验证证据。区分方案快照与当前事实；有冲突时说明差异，以当前可核实证据判断，缺失信息不得猜测。

明确区分本站目标和验收条件、当前任务线目标和完成条件、项目最终目标和完成条件。任务线达到交付条件即可结束；项目未完成不等于本任务线必须继续。由其他任务或集成线接手的事项明确交接，不追加为本任务的新步骤。不得降低验收标准、删除未完成项或改写目标以宣布完成，也不得自行恢复暂停事项、增加可选优化或扩大范围。

二、核对站点头尾和交接

本站头部列出任务线、步骤编号和名称、方案出处及版本（无版本号则记录日期和章节）、目标、范围、前置条件及逐项验收条件。
本站尾部列出实际完成内容、交付物、相关提交、验证证据、逐项验收结果（通过 / 未通过 / 待核验）、未决事项及其阻塞影响、是否达到本站目标、建议下一步编号及内容。
已编写、已提交或已有交接记录不等于验收通过；证据不足标为待核验。已通过且未受影响的验证不重复安排。

本站验收通过后，比较尾部下一步与方案中合法后继的编号、目标、工作范围和交付要求；措辞不必逐字一致，但含义不明确或存在冲突时标为待核验。逐一核对下一站全部前置条件，包括其他任务线依赖；分叉时分别核对每条后继，合流时核对全部必要前置。交接通过仅表示可开始，不表示已开始。
本站未通过则继续本站的必要修复或核验；依赖未满足则等待并指明对象和条件。建议超出原方案或需要改变目标时，标记方案变更待确认，不自行扩展路线。方案没有稳定编号时，可在不新增步骤的前提下建立对应编号。

三、选择且只选择一个结论

A. 本站未完成：继续本站必要工作。
B. 本站待核验：证据不足，先补齐必要核验。
C. 本站已完成，等待依赖：暂不进入下一站。
D. 本站已完成，可进入既定下一站。
E. 本任务线已完成，交付其他任务线接手。
F. 项目最终目标已完成。
G. 方案存在冲突或需要变更：等待明确决定。

选择 E 或 F 时明确写“本任务无下一步执行指令，到此结束”。其他任务线的交接事项或独立建议不能写成本任务继续执行的要求。不得为了填写下一步而编造工作。

四、固定输出格式

【路线核对】
- 日期：
- 开发项目 / Codex 项目文件夹：
- 任务线名称：
- 仓库 / 工作树 / Git 分支：
- 方案依据及版本：
- 任务线最终目标：
- 当前步骤编号及名称：
- 各项本站验收结果及证据：
- 本任务线剩余的既定步骤：
- 与最初方案的差异：
- 结论：A / B / C / D / E / F / G
- 判断依据：

不明确的信息写“待核实”。剩余步骤只能来自方案；无法核定时说明原因，不编造数量。

【可复制执行指令】
仅 A、B、D 输出，并放在一个完整文本代码块中，包含：任务线及步骤编号、任务名称、仓库/工作树/分支和所属文件夹、方案路径及版本和章节、本站目标、范围边界、前置条件、必要执行步骤、逐项验收方法和预期证据、按可验证阶段提交 Git 且不纳入无关改动、完成或阻塞时的停止条件，以及下列完成回执。执行指令应可脱离当前聊天独立执行；完成本指令后仅报告交接状态，不自动执行下一站。

任务名称正文前必须添加与该步骤在原方案中顺序一致的圈号，使用①②③④⑤⑥等样式。原方案第几个步骤就使用第几个圈号，不使用本次指令的章节序号，也不因继续或核验而重新编号；原步骤编号仍保留。例如执行 M05 时写“⑤ Codex 任务状态监测工作台实施任务线 / M05：实现可复制指令、结束回执及方案变更展示”，执行 M06 时使用⑥。圈号放在任务名称前，不替换“1. 任务名称”等章节标题。无法核定原方案顺序时标为待核实，不猜测圈号。

【执行完成后必须返回的回执】
- 日期：
- 方案文档为：完整路径、版本或日期及对应章节
- 本方案一共为：共 xx 步；分别是：

  1. 步骤编号及名称
  2. 步骤编号及名称
  3. ……（按原方案完整列出）

- 本次执行步骤为：方案中的步骤编号及名称；涉及多个步骤时逐条列出
- 本步骤是否完成：是 / 否 / 待核验；涉及多个步骤时逐条判断
- 是否满足方案预期：满足 / 不满足 / 待核验；涉及多个步骤时逐条判断
- 任务线 / 步骤编号：
- 本站原定目标：
- 实际交付：
- 提交及验证证据：
- 各项验收条件及结果：
- 当前阻塞：
- 任务线是否已到终点：
- 下一站：原方案编号及目标 / 无；多个后继逐条列出
- 本站尾部与下一站头部是否匹配：匹配 / 不匹配 / 待核验 / 不适用；多个后继逐条判断
- 下一站全部前置条件是否满足：
- 交接对象：本任务线 / 其他任务线名称 / 无
- 结束结论：继续本站 / 等待核验 / 等待依赖 / 可进入下一站 / 本任务线结束 / 项目结束 / 方案变更待确认

回执严格按上述顺序输出：日期后先列方案文档、方案总步数及完整步骤清单、本次执行步骤、完成情况和是否满足方案预期，再接其余内容。完整步骤清单必须使用缩进的有序列表，每个步骤独占一行，使用从 1 开始的连续编号，格式为“数字 + 英文句点 + 空格”，与父项之间保留空行；不得将多个步骤用分号串在同一段内。方案总步数和步骤清单必须来自所引用方案的既定步骤，不把本次指令的操作子项当作方案步骤；无法核定时写“待核实”并说明原因，不编造数量或步骤。完成情况和预期判断须由后续验收结果及证据支持，不重复输出同义结论字段。

对于 C、E、F、G，输出等待、交付或结束回执，说明依据及恢复条件（如适用），不要生成虚假的下一步执行指令。不得虚构项目现状，或将未经验证的工作报告为已完成。
```

二、先确定终点，再决定有没有下一步

明确区分：
1. 本站步骤的目标与完成条件。
2. 当前任务线的目标与完成条件。

不得通过降低验收标准、删除未完成项或改写原目标来宣布完成。

三、核对本站的头和尾

本站的头：
- 所属任务线、步骤编号和名称。
- 方案出处及版本；没有版本号时记录文档日期和章节。
- 任务目标。
- 前置条件。
- 明确、可验证的完成条件。

本站的尾：
- 实际完成内容。
- 交付物、相关提交及验证证据。
- 每项完成条件：通过 / 未通过 / 待核验。
- 未解决事项是否阻塞本站完成，以及依据。
- 是否达到本站原定目标。

“已编写”“已提交”“已有交接说明”不能直接等同于验收通过。
缺少证据时标为待核验，不得推断为完成。
已通过且未受本次改动影响的验证，不重复安排。

四、下一步必须来自既定路线

只有本站已满足完成条件，才判断能否进入方案中的下一站。

必须核对：
- 本站尾部提出的下一步编号、目标和交付内容；
- 原方案下一站头部规定的编号、目标和交付内容；
- 下一站所需的全部前置条件，包括其他任务线的依赖。

编号、工作范围、交付要求必须一致，不要求措辞逐字一致。

如果本站未通过：
仍停留在本站。只列满足原验收条件所必需的修复或核验，不伪装成推进到下一站。

如果下一站的依赖未满足：
标记等待依赖，说明等待谁、等待什么，不生成无关替代工作。

如果建议的下一步不在原方案内，或必须改变原有目标：
标记方案变更待确认，说明原因和影响，不自行扩展路线。
没有稳定步骤编号时，可以按原方案建立对应编号，但不得借此新增步骤。

五、明确选择一个结论

结论只能为以下之一：

A. 本站未完成：继续本站必要工作。
B. 本站待核验：证据不足，先补齐必要核验。
C. 本站已完成，等待依赖：暂不进入下一站。
D. 本站已完成，可进入既定下一站。
E. 本任务线已完成，交付其他任务线接手。
F. 项目最终目标已完成。
G. 方案存在冲突或需要变更：等待明确决定。

选择 E 或 F 时：
明确写“本任务无下一步执行指令，到此结束”。

【可复制执行指令】
