## 1. 接入目标及采用方式

用户继续使用现有 Codex 聊天，工作台能够发现并选择聊天、确认任务归属，通过项目授权的 MCP 工具接收方案草稿、开始、阻塞、回执和核验候选。当前宿主支持的 hooks 补充运行事件，工作台根据证据和既有领域规则显示路线位置与验收结果。

主路线为本项目独立实现 Windows 适配，复用标准协议库和现有领域服务。Monitor 的目录发现、被动观察和信号过期策略作为参考，具体复用代码在取得固定来源、许可及平台验证后逐模块决定。

接入分成三个能力层，界面分别显示是否可用。

| 层级 | 职责 | 验收范围 |
|---|---|---|
| 业务输入层 | 现有聊天经 MCP 与 Skill 提交结构化操作 | 本期核心，必须在目标 Windows 宿主实测 |
| 运行事件层 | 当前宿主可用 hooks，加上明确来源的只读历史读取 | 按每类事件和执行环境记录覆盖范围，缺失时显示未知 |
| 被动实时观察扩展 | 接入已有桌面内部 IPC，或终端环境可用的共享 App Server | 单独能力门槛，兼容失败时关闭该适配，保留核心业务入口和错误状态 |

本方案与 [04 组合方案](04_任务工作台MCP与Skill插件组合_可执行开发方案_2026-11-09.md) 共用服务和身份契约，细化 [02 原开发方案](02_桌面工作台与顶部常驻面板_可执行开发方案_2026-11-09.md) 的 D01、D03、D05。正式桌面产品仍按 D07 报告全部要求及未通过项。

## 3. 发现、身份与绑定

### 3.1 本地只读发现

沿用 02 第 4 节，按用户选择的 Codex 数据根目录发现目录元数据、索引、正常/归档会话，并按需解析文件。处理数据根覆盖、压缩/轮转、半行、锁等待、损坏、截断、相同会话的冲突变体及子会话。读取活动 SQLite 时遵循 WAL 一致性，不以强制 immutable 或删除锁文件绕开锁。

首次扫描建立基线，历史结束记录只出现在历史视图。索引中的标题与 cwd 用于显示及关联建议。应用按读取结果报告完整、不完整、不支持格式、读取失败的数量和范围。

### 3.2 身份映射

| 标识 | 定义及约束 |
|---|---|
| `hostId`、`dataRootId` | 本地主机和所选源数据根身份，区分相同 UUID 的不同来源 |
| `sessionId` / `threadId` | Codex 来源的稳定会话身份，保留 provider 和父会话信息 |
| `sourceId` | 现有工作台 `model.chats[].id`，与上方外部源键显式映射 |
| `projectId`、`folderId`、`taskId` | 工作台现有容器和任务关系，使用服务端真实 ID |
| `stationId`、`planId` | 现有站点及不可覆盖的方案版本，沿用 `model.currentPlanId` |
| `bindingId`、`bindingRevision` | 新增来源映射的稳定 ID 和版本，由服务端创建 |
| `executionId` | 本站一次执行标识，桥端为新操作生成唯一值，同键重试复用，服务端校验冲突 |
| `turnId` | 宿主轮次标识，与 executionId 建立来源关联，一次业务执行可跨多轮 |

工作目录组与 Codex 侧栏项目身份分别保存。只有实际读取到可靠侧栏身份时才建立外部项目引用。目录同名、相同 cwd 或相近时间只生成候选关联。

工作台提供聊天列表、搜索和站点选择，用户一次确认任务与一个或多个聊天。一个聊天涉及多个任务时，每次实际开始指定站点及 executionId，后续事件按明确关联归入对应执行。未知归属的事件进入待匹配区，避免落到最近点击的站点。

### 3.3 调用方声明与可信来源

普通 MCP 参数中的 threadId/sessionId 保留为调用方声明。通过本地索引能证明该来源存在，当前请求是否来自该聊天仍需宿主上下文、已验证事件关联或用户确认。

服务端返回 `sourceTrust` 与缺失原因，建议值为 `declared`、`userConfirmed`、`hostObserved`。工作台界面显示相应来源说明。字段缺失时提示用户从候选列表确认，当前助手的专有聊天管理工具和环境变量只在其正式可用范围内使用。

绑定授权覆盖指定项目、来源、站点及版本。新聊天、fork、切换任务或修改方案时核对绑定适用性，历史执行继续指向原绑定版本。来源可信度变更追加记录。

## 4. 连接结构和单写者

首选安装包内的 STDIO MCP 桥。Codex 作为客户端启动桥，桥经受限本地 IPC 或带每用户凭据的私有回环连接访问单实例领域服务。桥程序及运行依赖随发行资源提供，普通用户无需安装全局 Node。

若实际宿主无法运行本地 STDIO，CX01 才验证受支持的 HTTP 连接路径及认证。服务位于哪台机器、执行器能否访问回环地址须明确，只有真实往返通过的配置才进入交付说明。

主窗口、顶部窗口、MCP 桥和 hooks helper 共用数据根锁与同一领域写入所有者。配置中的固定端口或 UI 截图只作诊断信息，正式桥经发行应用的连接发现机制定位所有者。

服务端管理项目授权、只读/草稿/发布/执行候选权限、令牌撤销和请求审计。凭据不写入 Skill、公开插件包、聊天正文或日志。私有接口除校验来源访问外还校验项目范围，低可信内容不能扩大授权。

显式退出后持久化停止标记，后台桥及 helper 暂停自动拉起，用户主动重开或恢复后继续。异常断开则以有界退避重连。既有配置合并和卸载只处理本插件拥有的条目。

## 5. MCP 工具与写入契约

工具名沿用 02 的六项工具，并在本方案增加阻塞和核验候选提交。所有工具定义以 CX01 冻结的 JSON Schema 为准。

| 工具 | 作用及输入要点 | 成功结果 |
|---|---|---|
| `workbench_get_project` | 授权项目内读取方案、站点、依赖、bindings、连接新鲜度，支持 draftId/requestId 或原幂等键结果查询 | 实际 ID、revision、规则版本和能力覆盖 |
| `workbench_put_plan_draft` | 原文、sourceHash、候选结构、目标、expectedRevision、idempotencyKey | draftId、revision、issues |
| `workbench_validate_plan_draft` | draftId、revision | 完整问题清单、发布差异和服务端确认摘要 |
| `workbench_publish_plan_draft` | draftId、expectedRevision、sourceHash、confirmationDigest、幂等键 | 实际 projectId、planId、revision 与持久化回执 |
| `workbench_record_start` | projectId/folderId/taskId/stationId/planId/sourceId、bindingId、executionId、开始依据及版本 | startId、executionId、sourceTrust、revision |
| `workbench_submit_receipt` | 同一执行和方案，deliveryVersion、实际结果、未决事项、逐项自述及证据引用 | 未核验 receiptId、requestId、revision |
| `workbench_record_blocker` | executionId、等待对象、原因、解除条件及幂等键，恢复时引用原 blockerId | 阻塞或恢复记录及 revision |
| `workbench_submit_review_candidate` | receiptId、deliveryVersion、逐项检查、方法、候选证据和明确未执行项 | reviewCandidateId 和待批准项 |

业务写入带 `expectedRevision`、`idempotencyKey` 及来源范围，桥将预期版本映射到现有 store 的 revision 契约。新草稿/新空项目使用服务端授予的创建范围。语义哈希在排除传输请求 ID 后计算，同键同内容返回原结果，同键异内容明确冲突。

服务器在同一可靠提交边界内保存业务结果、事件和幂等结果索引。响应丢失后通过原 requestId 或幂等键查询，得到已提交、明确拒绝、待处理或结果未知。同一逻辑操作优先使用原幂等键查询或重试，得到未提交的明确结果后才允许重新发起该操作。并发 revision 冲突返回当前 revision 和重新读取提示。

来源绑定与正式核验批准先通过已认证工作台 UI 操作。普通插件令牌具有只读和候选写入权限，发布仅在已授权范围内开放。工具输入里的 `reviewer` 或 `result=passed` 不能替代服务端核验授权。

核验候选单独保存，与现有正式 `receiptLog.reviews` 分离。授权批准或受控验证器生成的结果才能调用现有 `action='review'` 路径。保留 `headDigest`、deliveryVersion、证据适用性和复验规则，并增加可验证的 actor/provenance。历史人工核验按原迁移记录保留来源标签。

## 6. hooks 与会话事件

### 6.1 初期事件映射

| 原始来源 | 归一化状态 | 业务影响 |
|---|---|---|
| `SessionStart` | 会话启动/恢复、来源候选 | 建立来源观察记录 |
| `UserPromptSubmit`、`PreToolUse` | 本轮有活动或工具开始 | 具备执行绑定时更新运行活动，本站开始仍通过开始门禁 |
| `PostToolUse` | 工具结果可用 | 保存有界摘要/检查产物引用及 provenance |
| `Stop` | 轮次结束候选 | 等待明确回执或进一步来源核对 |
| `Interrupt` | 中断 | 运行状态标为中断，保留未核验交付 |
| 已验证宿主等待事件 | 等待输入/审批 | 有真实请求身份时显示等待对象 |
| `SessionEnd` | 来源关闭 | 记录来源生命周期，任务验收单独计算 |
| 索引或 rollout 记录 | 历史或补充事实 | 标明来源和时效，按完整记录边界增量读取 |

当前 hook 列表和载荷必须以目标宿主实际事件证明。`PermissionRequest` 如可观察只记录等待，审批继续由原宿主处理。读取等待事件失败时明确等待对象未知。

插件 hooks 默认仅报告观察结果。`Stop` helper 返回宿主接受的空/中性 JSON，不返回阻止或继续执行决策。此处根据官方文档选择观察型行为，避免一次状态上报引入额外执行轮次。[Hooks 事件与 Stop 语义](https://learn.chatgpt.com/docs/hooks)

### 6.2 事件信封及新鲜度

归一化信封至少包含 schemaVersion、eventId、sourceKind、hostId、dataRootId、sessionId、可选 turnId、bindingId、executionId、类型、发生时间、接收时间、源序号/检查点、摘要、完整性及可信等级。无法读取的标识保存缺失原因。

宿主提供稳定事件 ID 时保留它。无原生 ID 时 helper 在本地入队时生成 UUID，持久化后重试复用。读取文件事件以文件指纹和完整记录边界构建稳定定位。跨来源事件通过已确认 sessionId/turnId/executionId 合并，缺少关联依据时保留多个出处并标记待核对。

运行观察有效期初始为 120 秒，UI 显示最后活动时间与来源。120 秒只是信号过期阈值，长工具无新事件时可显示“暂无新活动，执行状态未知”。已接受的开始声明仍在执行历史中，不因连接超时被写为完成。

业务展示增加 runtimeState、runtimeFreshness、业务执行状态和验收结果三个并列投影。复用现有 `inspectMonitor` 的验收/关闭计算，同时补充来源新鲜度与有效执行结束记录，避免旧 start 记录让面板长期显示正在执行。

### 6.3 投递与恢复

本地 helper 从 stdin 解析结构化事件，输出遵循宿主协议。桥和 helper 均在受支持执行环境中运行，安装包带齐所需运行组件。stdout 只输出协议内容，诊断写入脱敏 stderr 或本机日志。

初始投递预算为 500ms，超时后写入每用户有界 spool，再中性退出。spool 初始总量上限 10MB、保留 24 小时，按 eventId 防重并优先合并重复活动信号。越限或写盘失败记录丢失计数及覆盖缺口，执行控制继续由宿主负责。工作台重开后按来源序列/检查点补投，过期活动事件只补历史。

宿主只支持 MCP tool hooks 时复用已有连接，并实测启动时连接尚未就绪的情况。普通 Skill 的明确操作可独立提交业务记录，hooks 覆盖范围单独显示。更新后涉及 hook 定义或脚本变化时使用宿主审阅与信任流程。[官方 hooks 安装与环境说明](https://learn.chatgpt.com/docs/hooks)

## 7. 插件、Skill 与现有聊天生效

拟建 `plugins/task-workbench/` 包，根 `plugin.json` 保存身份及 OpenAI 扩展，`mcp.json` 保存实际 MCP 配置，`skills/` 放单一 Skill `workbench-handoff`，`hooks/` 放已验证的观察配置。兼容清单仅在当前安装版本需要时生成，避免同时维护彼此冲突的配置来源。

单一 Skill `workbench-handoff` 的职责及验收归 04 第 7 节，所需工具名与本文件第 5 节保持一致。服务返回 schema/ruleVersion 和 supportedCapabilities，Skill 遇到未知版本时显示兼容问题，避免自行推测参数。

插件打包、安装及路径由 CX01 固定的官方 schema 校验。用户从当前 UI 支持的插件包或个人市场安装，诊断聊天检查工具与 Skill 可见性，然后在现有目标聊天验证刷新或续接。既有聊天尚不可加载插件时，保留原会话和绑定，将状态明确为能力待恢复，并提供诊断聊天验证服务的入口。

只有实际 MCP 请求到达，才能显示“已收到 Codex 调用”。分开显示插件已安装、桥就绪、项目已授权、目标聊天可调用、hooks 已信任、源读取可用和被动观察可用。[官方插件打包](https://developers.openai.com/plugins/build/plugins)、[官方 Skill 开发](https://developers.openai.com/plugins/build/skills)、[官方插件安装](https://learn.chatgpt.com/docs/plugins)

## 8. 被动实时观察扩展门槛

Windows 桌面 IPC 和 CLI 共享 App Server 使用独立 adapter，能力表分别记录。内部 IPC 模块默认关闭，只有在目标版本和选定源范围完成只读验证后启用。用户数据和源设置仅按已授权范围访问。

| 验证项目 | 必需证据 |
|---|---|
| 通道归属 | 端点来自真实运行实例，同用户/主机范围可确认，连接来源与目标进程身份对应 |
| 观察语义 | 接入前后原会话持续运行，观察器不会自动 resume、启动轮次、发消息、回答审批或终止源任务 |
| 能力与范围 | 指定桌面/CLI 版本、编排模式、实际连接协议和可观察事件完整列表 |
| 断线与版本升级 | 正常关闭、崩溃和未知协议时解除观察并显示 unknown/unsupported，保留业务历史 |
| 隐私与体量 | 对话快照及时归一化，正文按用户选定范围按需读取，避免把整份源快照写入 UI 状态和日志 |

官方 App Server 的 `thread/resume` 等操作可能改变服务端线程加载/订阅状态，采用前必须核对语义和实际影响。连接新启动的私有 App Server，只能声明实际可见的线程范围。Monitor/macOS 或 Openbar/CLI 的演示单独保存参考出处，Windows 桌面验收另留记录。

扩展阶段可以记录未知协议缺口并给出恢复条件。组合发布说明必须保留被动观察覆盖范围，不能用已连接 MCP 的成功记录填充 IPC 验收项。

## 9. 阶段、前置和验收出口

| 阶段 | 工作 | 验收出口 |
|---|---|---|
| CX01 当前宿主能力探测 | 锁定 Windows/宿主/执行环境版本，隔离最小 MCP 工具、Skill 和插件加载，确认实际会话发现及绑定方式 | 真实工具往返回执，源目录读取证据，能力表及清单 schema，缺口和恢复条件 |
| CX02 发行桥与请求契约 | 安装资源、单实例发现、项目授权、幂等/revision、查询、撤销与停止标记 | 并发、重复、响应丢失、跨项目拒绝、显式退出与主动恢复通过 |
| CX03 任务绑定与业务上报 | 来源列表、确认绑定、草稿发布、开始、阻塞和回执，接入 `workbench-handoff` 与其生成指令的工具登记流程 | 现有聊天真实闭环，ID 和版本可回查，同目录歧义及跨聊续接通过 |
| CX04 hooks 及状态归一化 | 支持环境内的事件 helper、spool、去重、新鲜度和运行投影 | 真实事件、未信任/不支持/断线状态、重复/乱序/长工具及中断负例通过 |
| CX05 核验与可选观察扩展 | 核验候选和正式批准分权、受控验证器、证据适用性，按第 8 节验证 IPC/CLI adapter | 候选无法直接通过，真实核验有效，扩展逐项记录兼容门槛结果 |
| CX06 安装后端到端 | 插件首次安装、更新、原聊天生效、真实模型调用、工作台/面板同步、恢复卸载 | 04 的组合场景及本节负例通过，所有适用范围与限制可追溯 |

CX01 与原 D01 的验证共用证据，CX02—CX05 承接 D03—D05。FX 动效另按 03 验收，C06/D07 最终组合核对。

必需负例覆盖以下情况。

- 相同 cwd 中两个任务或两个聊天，缺 sessionId、fork、旧绑定、来源自报伪造。
- 旧 planId、revision 冲突、依赖未就绪、同执行重复开始、不同执行冲突。
- 客户端自述通过但证据缺失，普通令牌提交正式 review，证据对应旧交付。
- 写入已提交但响应丢失、重复 hooks、乱序事件、单源重放及跨源归属不明。
- `Stop` 后继续新一轮、Interrupt、源服务退出、运行活动过期、历史首次导入。
- hooks 未信任、脚本路径含空格/中文、执行器不在本机、HTTP/STDIO 不可达、启动早于 MCP 就绪。
- 桥和桌面同时启动、用户显式退出、进程崩溃、待投递队列越限、授权撤销、安装更新及卸载恢复。

每项保存日期、版本/源提交/安装包哈希、宿主环境、具体操作、预期、实际、脱敏回执和证据位置。自动化测试采用隔离项目和固定样本，真实接入至少完成一个已有聊天及一个诊断聊天，并证明两者归属正确。

## 10. 拟定模块和交付材料

拟建 `app/mcp/` 承担协议桥，在 `app/server/` 中增加来源绑定、归一化事件和持久化请求结果模块。复用既有 `model-store.mjs`、`receipts.mjs`、`monitor.mjs` 和模板输出。正式核验角色校验覆盖服务实际写入入口，新增模型字段需 schema 与旧数据副本回归。

为跨来源 execution/turn、绑定及 checkpoint 建立独立版本化记录，正式业务身份引用现有 model。对 IPC 和平台读取接口做小范围隔离，未知字段保留解析版本与错误状态，防止平台差异进入领域规则。

交付至少包含以下材料。

1. 当前宿主能力矩阵与本机验证回执。
2. 桥程序、插件包、单一 Skill `workbench-handoff`、必要 helper 及精确版本/哈希。
3. 工具 schema、错误码、权限矩阵、请求幂等和数据迁移说明。
4. 插件包/个人市场安装、现有聊天刷新、hooks 审阅、项目授权和撤销操作说明。
5. 一次真实“方案 → 绑定 → 开始 → 阻塞/解除 → 回执 → 核验”的记录，以及失败恢复负例。
6. 被动观察适配的支持范围、协议版本、已知限制和禁用方法。
7. 数据备份恢复、显式退出、卸载恢复及第三方许可记录。
