## 1. 本轮目标

为当前工作台开发本地 Codex 插件，将方案整理、站点执行与修复、核验与交接流程带入用户现有聊天。插件通过 MCP 连接工作台，由工作台保存总方案、分支/工作树/会话归属、修复历史、证据与全局进度。

## 4. 修复与回归业务模型

### 4.1 工作上下文

在 05 的 projectId、folderId、taskId、stationId、planId、sourceId、bindingId、executionId 和 turnId 基础上，增加 `workContext`。

- `repositoryId` 与 `worktreePath` 标识仓库和工作树，仓库根路径来自授权范围内的实际读取。
- `branchName`、`headCommit`、是否 detached HEAD、dirty 状态和交付内容指纹标明代码现场。
- `sourceId` 关联聊天，`executionId` 关联一次站点执行。路径、分支和短标题用于辅助显示，稳定业务关联仍由 ID 与确认记录决定。
- 分支改名、工作树搬迁或切换 HEAD 时重新核对上下文，追加版本。目录相同的多个任务仍需确认归属。

Skill 提交的是调用方观察或声明，服务按 05 的 sourceTrust 保存可信等级。授权范围可读取时核对 Git 上下文，读取失败就明确待核对。既有历史缺少上述字段时保留未知，不根据当前目录补写历史现场。

### 4.2 修复案例与尝试

| 对象 | 必需内容 |
|---|---|
| `RepairCase` | repairId、归属项目/任务/站点/方案、触发回执或失败条件、问题说明、预期结果、范围分类、关闭条件、回归锚点、状态与 revision |
| `RepairAttempt` | attemptId、repairId、executionId、sourceId、workContext、尝试目标、实际修改、交付版本、检查结果、证据引用和未决事项 |
| `ReturnAnchor` | 原始所属站点、适用 planId、应重新检查的条件与依赖、合法后继/合流引用，附生成时业务 revision |
| `ResumeContext` | 总目标、当前方案、当前站点、未决修复、最近有效交付、依赖与等待对象、下一步判定及依据 revision |

修复案例归在原站点下面，尝试历史追加保存。同一问题的再次修复沿用 repairId，新的尝试采用新的 attemptId/executionId。多个未决问题各有关闭条件，单项修复结束后继续核对本站其他条件。

每轮尝试结束时记录执行终态并提交对应回执，保留未通过条件。下一轮按当前差距登记新的 executionId，原尝试的结束记录和本站的验收资格分别计算。

范围分类采用原定交付、既定验收所需修复、新增范围候选和待确认。新增范围候选进入方案差异确认，批准后形成新方案版本。分类由规则和用户确认控制，AI 可提交分类建议及理由。

回归锚点在案例建立时保存。每次使用锚点均按当前方案、绑定、全部依赖和核验状态重新计算，原锚点用于追溯。旧方案的后继不直接成为新方案的执行指令。

### 4.3 修复结束与站点推进

修复状态建议为待确认、处理中、待核验、已解决、待复核。关闭候选由执行 Skill 或核验 Skill 提交，正式解决由相应条件的有效核验确认。站点通过仍要求全部必需条件及交接规则满足。

服务端返回 `disposition`，可取继续本站、继续指定修复、等待依赖、等待核验、交接后继、进入合流核验、结束任务线或结束项目，并携带判定依据、缺项和 revision。AI 可解释结果及提交新问题候选。

现有 A—G 判定、`outputs.mjs` 模板及 receipts/monitor 的正式关闭规则继续复用。新字段为修复级上下文补充，后继可开始与后继已开始分别记录。

## 5. MCP 工具契约

继承 05 第 5 节八项工具及同一服务端 schema，不建立插件私有的正式数据副本。本轮新增一项修复记录工具，并扩展现有上下文和回执返回。

| 工具 | 本轮细化 |
|---|---|
| `workbench_get_project` | 返回当前 `ResumeContext`、修复清单、工作上下文、全局依赖/合流条件、disposition 和 basisRevision，支持按站点读取必要内容 |
| `workbench_put_plan_draft` / `workbench_validate_plan_draft` / `workbench_publish_plan_draft` | 为新增范围候选提供出处和差异确认，发布时重新核对当前 revision |
| `workbench_record_start` | 登记 workContext，可选关联 repairId，校验站点与方案后建立执行 |
| `workbench_record_repair`，拟新增 | 建立案例或追加尝试/待核验结果，引用失败条件、归属站点、回归锚点和 executionId，服务端生成稳定 repairId/attemptId |
| `workbench_record_blocker` | 等待对象可关联修复、来源、前置站点、用户确认或合流交付，恢复引用原 blockerId |
| `workbench_submit_receipt` | 可引用 repairId/attemptId，提交交付与未决修复，接受后返回待核验状态及重新计算的 disposition |
| `workbench_submit_review_candidate` | 提交修复条件和站点条件的逐项检查候选，列明证据适用版本及未执行项 |

新修复工具的 schema 明确区分创建案例、追加尝试和提交解决候选，限定相应必需字段。所有写入遵守 expectedRevision、幂等键、项目范围和来源检查，同键重试返回原结果，同键异内容拒绝。解决候选无法直接写入正式核验或关闭状态。

回归判定在领域服务内生成，返回 revision 与上下文一起构成读快照。实际开始下一项工作前复查版本与依赖。多客户端修改后，旧建议以过期状态展示并重新读取。

核验权限、受控验证器和响应丢失回查沿用 04、05。普通插件只提交候选记录，正式核验通过已认证工作台入口或受控验证器。证据引用需对应实际交付内容，工作树未提交修改使用内容指纹补足单个 commit 的适用范围。

## 6. 三项 Skill 的执行流程

每个 Skill 提供简体中文说明、清晰触发条件、输入、工具顺序、输出、失败恢复和参考模板。名称为计划名称，实施后以宿主实际发现结果为准。官方支持用 `SKILL.md` 配合参考资料、模板和必要脚本组织工作流。[官方 Skill 开发指南](https://developers.openai.com/plugins/build/skills)

### 6.1 `workbench-plan` 方案整理

1. 取得原文、目标项目及授权范围，读取已有方案和版本。
2. 保留总目标、编号、站点范围、必需验收和终点，标出多线拆分、依赖、交接与合流节点。
3. 将缺失、歧义及新增范围保存为问题，提交草稿并校验。
4. 向用户展示差异和缺项，按已有授权规则发布，回查实际 projectId、planId、revision。
5. 输出路线摘要与仍需确认的绑定，后续操作引用真实 ID。

### 6.2 `workbench-execute` 执行与修复

1. 读取 ResumeContext，显示总目标、本站位置、当前差距和回归条件。
2. 核对聊天、分支和工作树，存在歧义时让用户从候选中确认，登记本次执行。
3. 修复任务先取得或建立 RepairCase，明确本轮解决的验收差距及范围。
4. 按已确认范围执行，每轮追加实际结果、检查、证据和未决项。新范围单独登记候选。
5. 提交回执并取得持久化结果，再读取最新上下文及 disposition。
6. 输出本站结论、未决修复、应回到的位置、合法下一步和等待对象。

用户说“继续修复”“换一个聊天继续”“下一步是什么”时，Skill 首先读取服务端上下文。源服务不可达时显示最近快照版本和缺失信息，恢复后再给出可执行的最新推进建议。

### 6.3 `workbench-review` 核验与交接

1. 读取当前方案、目标回执、修复案例、验收条件及交付版本。
2. 按条件实际检查，区分受控命令结果、人工审查、原生验证和用户体验确认。
3. 提交候选，列明已检查、失败、缺失和未执行项，交给授权核验入口处理。
4. 正式核验后读取 disposition，说明继续修复、等待、交接或结束的依据。
5. 合流时逐条核对上游交付版本和验收有效性，记录合流现场与整体测试结果。

Skill 引导核验和 Git 操作时沿用用户授权及仓库规则。工作台本轮记录交付和合流条件，实际分支创建、代码合并和执行由用户当前会话按授权操作。

### 6.4 标准结果结构

三项 Skill 的用户输出至少涵盖总目标和方案版本、当前站点/修复、实际完成内容、证据或缺项、回归位置、下一步判定及其 revision、服务持久化 requestId。任务线或项目有效结束时使用原模板结束句，并给出关闭依据。

模型遵循 Skill 的情况通过真实样例检验，服务端门禁负责拒绝不符合契约的操作。关键状态始终以实际接收和核验记录为依据。

## 7. 插件包和本地运行组件

拟定源码结构如下。LP01 固定当前宿主支持的最终清单格式，LP05 再生成实际发行产物。

```text
plugins/task-workbench/
  plugin.json
  mcp.json
  skills/
    workbench-plan/SKILL.md
    workbench-execute/SKILL.md
    workbench-review/SKILL.md
  references/
    workflow.md
    tool-contracts.md
  assets/
    自有图标和模板
  hooks/
    已验证环境适用的观察配置
```

参考资料和模板由各 SKILL.md 指明读取时机，模板优先由现有工作台生成或从同一版本化源产生。打包检查必须覆盖所有引用路径，插件声明契约版本范围，避免包内模板与服务规则漂移。

根 `plugin.json` 保存插件身份、版本和必要 OpenAI 扩展，`mcp.json` 声明真实本地 MCP 启动命令。以当前官方 portable 格式为首选，目标版本需要兼容清单时记录选择及验证结果。[官方插件打包指南](https://developers.openai.com/plugins/build/plugins)

MCP 桥和必要 helper 随工作台发行资源提供，运行依赖一并打包。通过宿主支持的插件路径解析或安装器生成配置定位实际程序，验证含空格、中文和搬迁后的路径。stdout 用于 MCP 协议，诊断进入脱敏 stderr 或日志。

桥只连接同一单实例领域服务，插件包保存连接配置和必要的有界待投递记录。单写者、授权撤销、停止标记、恢复和幂等索引沿用 05。源数据与凭据由本地授权机制管理，公开插件包和模板只包含可分发资源。

## 8. 安装、既有聊天与更新

1. 用户安装并启动工作台，进入插件连接页选择授权项目。
2. 安装当前宿主验证通过的本地包或个人插件市场入口。
3. 在诊断聊天检查 MCP 工具、三项 Skill、实际数据根与授权范围。
4. 在用户现有目标聊天验证刷新/续接和工具调用，确认来源与站点绑定。
5. 使用固定样例完成一次方案提交、两轮修复、核验及回归操作。

安装可见性与旧聊天生效分别验收。若目标聊天无法加载能力，记录宿主版本、恢复方法和未覆盖范围，保留原有任务与聊天的绑定关系。工作台显示安装、桥就绪、实际调用、已授权、Skill 可用和 hooks 覆盖的独立状态。[官方插件使用说明](https://learn.chatgpt.com/docs/plugins)

首版核心闭环依靠主动 Skill/MCP。hooks 作为已验证环境内的增强，观察式处理器只报告活动和中断，信任流程由宿主完成。云端编排、本地执行和桌面界面之间的能力差异按 05 的能力表验证。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)

插件升级时检查 schema 与服务版本，重新打包并检查引用文件。涉及 hooks 变更时按宿主要求重新审阅。卸载只移除本插件拥有的配置和运行入口，工作台业务数据按用户选择保留或导出。更新失败可回退插件包及配套运行组件，数据迁移按已验证的备份恢复步骤处理。

## 10. 必需验收场景
