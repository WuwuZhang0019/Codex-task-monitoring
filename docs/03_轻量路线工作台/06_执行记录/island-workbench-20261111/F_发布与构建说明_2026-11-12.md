## 构建方法

1. 根据交付清单核对源码 ZIP 的 SHA256，解压到独立空目录。源码 ZIP 由固定 Git 对象导出；不包含 .git、运行数据库、用户配置或令牌。优先从各本地仓库取得清单中的同一 Git 提交，使用干净 checkout 构建。若只用 ZIP，业务打包器需要 Git 记录来源，须在解压的 business-source 目录显式执行 git init -b codex/source-import、git add .，再以本地测试身份提交一次；这会产生新的“导入提交”，应同时保留交付 source-manifest.json 中的原提交及导入映射，不将两者冒称相同。不要修改用户全局 Git 身份。外壳构建不要求原 Git 历史。
2. 业务在 app 下使用满足 package.json 的 Node 与 npm，运行 npm ci、npm run build、npm run desktop:resources。资源脚本校验 Node 25.5.0 官方压缩包 SHA256，再将 Node、server/MCP bundle、前端和许可资源放入 app/desktop/resources。需要访问 npm 和 Node 官方分发站点，离线时只能复用已校验的原始分发压缩包与包管理器缓存。
3. 外壳使用 Bun 1.4.4 与本次验证 Rust/Cargo 1.98.0、Windows MSVC 工具链和 WebView2。执行 bun install --frozen-lockfile、bun run lint、bun run build、bun test；在 src-tauri 下执行 cargo clippy --locked -- -D warnings、cargo test --locked --lib。设置子进程 RUSTUP_TOOLCHAIN，不修改用户全局默认工具链。
4. 外壳执行 bun run tauri build --debug --bundles nsis --config src-tauri/tauri.nosign.conf.json。本次 NSIS 是用于本地交付的未签名 debug 构建，与 E 的验收构建类型一致；不是已经签名的公开正式发行。用独立 CARGO_TARGET_DIR 保存产物，不覆盖正在使用的安装版。release 优化、签名或自动更新上线须另行构建验证，不能沿用本包哈希。
5. 根 LICENSE 保留完整 GPLv3 文本，原创声明采用 GPL-3.0-or-later。保留两个仓库 SOURCE.md 和 THIRD-PARTY-NOTICES.txt。外壳安装资源 licenses/ 携带许可正文；业务资源包也携带原创、前端、server/MCP 和 Node 许可。

构建要求“从固定提交的干净 checkout 可成功构建”，不承诺不同构建时间/机器的安装包字节完全一致。最终生成命令与日志及源码选择脚本保存在 assets/F，文件清单用于复核。
