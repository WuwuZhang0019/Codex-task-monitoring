# 连续执行按钮与阶段会话调度

日期：2026-11-13

状态：已实现并更新本机运行版

## 使用方式

方案登记后，在任务列表中点击路线右侧、归档图标左侧的“连续执行”。按钮采用 [Uiverse warm-turtle-37](https://uiverse.io/nazar-gavrylyk/warm-turtle-37) 的滑动圆球样式，缩短为 102 × 28 像素，开启时为紫色，关闭时为灰色。

服务按照方案依赖选择尚未完成的必要主阶段，每个阶段创建独立 Codex 聊天。一个阶段中的子步骤由该阶段聊天执行，所有必要子步骤验收通过后才接续。已完成阶段会跳过；开启时如果已有阶段正在执行，则观察原有聊天与工作台结果，不重复派发。

关闭开关只暂停后续接续，当前阶段继续执行至结束。再次开启时复用当前未完成聊天或进入下一未完成阶段。失败、等待人工决定、来源变化或验收未通过时停下并显示原因。服务重启后保持暂停，用户点击后核验恢复。整个方案必须满足步骤与最终验收条件才能结束。

此功能使用用户已安装并登录的 Codex，通过公开 app-server 的 thread/start、thread/name/set、thread/resume、turn/start 及 turn/completed 创建与跟踪真实聊天。服务负责确定性调度，不额外创建 AI 总控聊天。聊天在已登记路线的目录中运行，沿用已连接 Codex 的权限；没有可用连接时不派发。不依赖开发者机器的项目目录，不修改 Codex 私有数据库。

本次交付是单个已登记方案的阶段连续执行。多分支项目文件夹初始化、跨项目并行运行和 Git 合并自动化不属于本次已验证范围。

## 双模式设置与启动反馈修复

日期：2026-11-13

状态：已完成，已更新本机运行版

用户录像中的三类情况已经分别定位：返回值测试方案 01、02 已完成，按钮实际禁用；二十步骤模拟方案登记的工作目录不存在，启动后立即受阻；正式实施方案原文与登记哈希不一致，被普通异常转换成服务端 500，原生层进而只显示 `CONTINUOUS_RESULT_UNKNOWN`。

本轮将目录与分支、方案原文等校验前移到开启请求。可确定的拒绝返回带中文原因的 409，不先显示启动成功。不会自动创建缺失的示例工作树，也不会用当前文件覆盖已登记方案版本。用户通过正式修订入口同步新版本后，只能在当前责任已验收、旧调度已退出的边界恢复，并保留旧运行身份索引与会话历史；未验收阶段仍保留原绑定与执行身份，要求先核对。

设置新增独立“连续执行”页，保存 `tasks.continuousMode`。切换偏好本身不派发任务，下次开启、恢复或重试时采用所选方式：

| 设置选项 | 模式 | 行为 |
| --- | --- | --- |
| 阶段完成后接续新会话（默认） | `stages` | 跟踪当前阶段结果，验收通过后为后续阶段创建独立会话；阶段内部子步骤遵循原方案 |
| 立即通知当前会话持续执行 | `current_thread` | 已有阶段执行时立即向其真实会话发送指令；后续阶段验收与绑定依次推进，继续复用该会话。没有执行会话时创建首个会话后持续复用；涉及不同工作树时明确拒绝 |

两种模式均遵循依赖、实际证据及最终验收门禁。当前会话模式向执行者明确限定本阶段及其子步骤，阶段验收通过后再发送下一阶段，避免执行者和调度器同时派发。关闭只停止后续接续，当前阶段继续完成。

运行状态与用户开启意图分开保存。受阻时保留 `enabled=true`，按钮显示琥珀色“接续受阻”，卡片持续显示原因及“重试”；用户仍可点击开关关闭。已完成方案统一显示“已完成”，包括没有连续运行历史的已完成方案。等待当前阶段、发送指令和准备后续会话均有明确反馈。

外部桌面会话使用已安装官方 Codex App Tools 的标准 MCP 接口，仅调用 `read_thread` 与 `send_message_to_thread`，精确限定已登记的 threadId 与 local 宿主。只使用宿主明确授予的连接与调用方身份，不扫描管道、不持久化连接信息、不另起 app-server 接管外部活跃会话。独立执行器创建的会话使用 app-server；运行中追加指令带 `expectedTurnId`。发送结果未知时保留检查点，禁止盲目重发；需要人工批准或输入时明确受阻。

运行条件：当前会话方式要求后台获得 Codex 桌面授予的会话控制连接。普通独立启动且没有此连接时显示具体原因；按阶段方式仍可使用。桌面消息接口确认的是已发送，客户端不一概声称所有宿主都使用实时 steering。
