## 目标与职责

提供一个流程入口，指导 Codex 读取原方案、提取路线、组织会话并按时调用 MCP。Skill 将现有方案的执行步骤编号规范为工具格式，保存旧编号映射，并建立会话与步骤的关联。

## 开发内容

1. 核对现有 `workbench-handoff` 的职责、工具使用和规则，确定复用或修订范围，形成单一入口的使用说明。
2. 登记流程读取原文及来源版本，提取步骤、内容、验收、依赖和工作树分配。含糊或缺失的前置保留待确认，提交结构化草稿并处理校验反馈。
3. 会话组织流程根据实际任务分组分配 A、B、C，生成文件夹与会话名称，调用可用的绑定和宿主操作能力。
4. 开始流程读取最新快照，核对绑定、目录、分支和前置，提交本次执行与当前步骤开始事件。
5. 过程流程在步骤开始、验收通过、阻塞、恢复、取消或返工时上报。普通调试和自动重试继续记录在当前步骤。
6. 结束流程提交结果、验收证据、未完成事项及相关步骤快照，读取保存回执，明确本次结束原因。
7. 接续流程读取现有状态，查询未确认事件，沿用同一次逻辑执行标识，处理版本冲突后补报。
8. 计划外独立事项记录来源及阻塞关系，按用户授权处理规划和执行范围。

## 与其他模块的约定

Skill 使用 MCP 已声明的能力，保存回执决定同步结果。路线模块检查业务状态，存储模块处理可靠提交。无法上报时说明待同步内容并留下可恢复记录。

## 验收

在真实聊天中分别验证首次登记、单会话多细分步骤、工作树分配、正常结束、等待用户、阻塞恢复和新会话接续。检查步骤编号规范化及引用更新正确，重复处理保持稳定，工具调用记录能对齐实际工作。

## 交付

Skill 源文件、必要参考资料、安装或插件打包说明，以及真实调用记录。具体工具名在 MCP 契约确定后绑定。

## 总 Skill 入口与按需加载设计

日期：2026-11-10

状态：组织方式已确定，阶段编排待后续细化

沿用 `workbench-handoff` 作为用户调用的总 Skill，各流程通过 `references` 按需加载。总入口负责判断当前任务、读取当前流程所需资料、检查阶段出口和保存执行位置。用户可使用以下入口，并附方案的实际完整路径。

```text
使用 $workbench-handoff，接入这个方案并开始执行。
```

当前文件组织继续复用，后续按流程独立维护的需要拆分关联与补充事项，以及执行与恢复参考。以下为目标组织，context-binding.md、recovery.md、supplements.md 待后续拆分时建立。

```text
workbench-handoff/
├── SKILL.md                         总入口、流程选择与共享约束
└── references/
    ├── plan-registration.md          方案提取、编号与登记
    ├── context-binding.md           会话与工作树分配、绑定
    ├── execution-sync.md            开始、状态更新与结束
    ├── recovery.md                  中断恢复、重试与换聊接续
    ├── supplements.md               补充事项处理
    ├── handoff-workflow.md           核验、下一步与交接
    └── handoff-template.md           交接输出模板
```

当前 context-supplements.md 承担关联和补充事项规则，execution-sync.md 同时承担恢复规则。拆分时更新入口链接并保留全部既有行为。其他项目或入口确有独立复用需求时，再评估提取独立 Skill。

### 阶段出口

| 阶段 | 读取内容 | 进入下一阶段的条件 |
|---|---|---|
| 导入方案 | 原方案、编号映射、登记规则 | 步骤识别与依赖校验通过，取得发布保存回执 |
| 分配工作树与会话 | 当前步骤分组、实际目录与分支、关联规则 | 必要绑定有效，宿主操作结果明确，执行前置满足 |
| 执行任务 | 当前步骤、相关前置、验收和执行规则 | 步骤切换时核对必要状态，本次结束时核对结果与证据并取得回执 |

用户已授权连续推进时，出口满足后自动继续。歧义、授权缺口或失效前置影响当前阶段时，记录等待条件。入口加载当前阶段所需规则，检查点记录用于后续恢复。

### 插入请求与最小恢复上下文

- 核对进度时读取当前快照，答复后回到原步骤。
- 修订方案时先判断对当前步骤的影响。涉及范围、依赖或验收变化时，保存执行位置，重新修订和校验，按影响范围重新检查前置。
- 补充独立事项时先记录来源和阻塞关系，按已有授权处理，再回到可继续的原步骤。
- 恢复时读取方案来源版本、当前步骤及执行 ID、绑定版本、变更部分、相关前置、未确认事件和证据位置。规则文件拆分仍在同一聊天上下文中运行，按需加载和简短检查点共同控制重复读取。

## 状态、验收与交接结论的对应

日期：2026-11-10

状态：规则已确定，真实状态写入待验证

步骤五状态、验收记录、执行结束原因及 A—G 交接结论分别保存。A—G 针对本次核对范围按全局证据选择，多个步骤的业务状态可同时存在。

| 场景 | 步骤状态与验收处理 | 交接处理 |
|---|---|---|
| 已交付代码，必要验收未执行或证据不足 | 保留执行中并记录待核验；确需外部条件且无法继续时登记阻塞 | 本站待核验选择 B |
| 验收发现缺陷，仍在原范围内修复 | 保留执行中；已完成步骤需显式 reopen 并保留完成历史 | 本站未完成选择 A |
| 当前站全部条件满足，其他线前置未满足 | 本站按验收依据提交 completed，后继保持待执行并列等待对象 | 选择 C |
| 本站完成且下一站全部前置满足 | 保存本站完成依据，后继实际开始时再提交 running | 选择 D |
| 需要用户确认且当前步骤无法继续 | 已开始步骤登记 blocked，未开始步骤保持 pending，保存等待对象和解除条件 | 验收确认归 B，范围或方案冲突归 G，其余按本站条件判断 |
| 本次聊天或执行结束，方案还有剩余步骤 | 按实际结果保存各步骤状态，单独记录执行结束原因 | 按全局范围选择 A—E 或 G |
| 任务线或项目全部必要条件满足 | 核对全部必要步骤、依赖及验收，完成依据可追溯 | 任务线完成选择 E，项目目标完成选择 F |

写入的保存回执证明事件提交结果。completed 还须满足配置的验收条件；存在必要用户体验确认时，将其纳入验收清单。返回成功后回读状态及证据，冲突或结果未知时保留同步问题和原事件键。

## 补充事项分类与阻塞解除

日期：2026-11-10

状态：分类及历史关联规则已确定

以原方案验收范围和实际目标判断分类，必要时展示判断依据并确认歧义。

| 例子 | 分类与处理 |
|---|---|
| 修复原步骤要求的保存失败、补齐原验收所需检查、自动重试 | 在原步骤追加进展、修复及证据，沿用原验收 |
| 新增原方案未要求的导出功能，或另行安排且有独立验收的任务 | 登记补充事项，记录来源、目标和授权范围，按确认结果规划关联方案 |
| 执行中发现外部模块必须独立修复才能继续 | 登记独立补充事项并标记 blocksSource，同时登记来源步骤的对应阻塞 |
| 目标与原验收的关系不明确 | 保留待确认分类及依据，完成不受该歧义影响的已授权工作 |

分类调整时保留原 repairId、supplementId、来源步骤和历次处理记录，记录调整原因与新关联。同一事项重试复用原身份。普通修复转为独立事项时建立关联；独立事项归回原步骤时记录归并依据和后续承接。

resolve 或 cancel 仅处理该事项对应的阻塞来源。完成需要核对关联方案必要交付，取消必要事项需要明确替代承接。随后重读来源步骤的全部阻塞和前置，满足条件时恢复 running；来源步骤完成仍需自己的验收依据。

## 当前任务推理等级推荐

日期：2026-11-10

在首次接入、开始执行或生成下一步指令时，根据当前步骤的歧义、跨模块依赖、故障定位难度、变更影响及验收复杂度给出推荐。任务范围发生显著变化时重新评估，同一任务内保持简短，避免重复提示。

官方部署检查清单列出五个推理档位 `low`、`medium`、`high`、`xhigh`、`max`。GPT-6 Sol 和 GPT-6 Luna 另支持 `none`，合计六种取值；GPT-6 Astra 和 GPT-6.1 Sol 支持前述五档。模型支持情况按当前官方文档与实际宿主确认。

| 任务特征 | 推荐推理等级 |
|---|---|
| 提取、分类、路由、常规文字修改或明确单点操作 | `low` |
| 常规功能实现、局部修复、明确验证路径的方案编写 | `medium` |
| 跨模块推导、事务与恢复排查、复杂依赖或根因诊断 | `high` |
| 复杂任务已有代表性评估证明进一步推理有质量收益 | `xhigh`，同时说明评估依据及额外耗时、资源取舍 |
| 最困难任务已有评估证明最高档位值得额外消耗 | `max`，同时列出相对较低档位的收益证据 |

推荐必须给出一个明确档位和一句依据。例如“建议推理等级 high。当前任务涉及事务、幂等与恢复的一致性，需要跨模块推导。”生成执行指令时将建议放在指令前，保持既有回执字段顺序。单凭文件多、耗时长或多轮失败不足以推荐 xhigh 或 max。

当前模型未知时给出明确条件建议，例如“建议 high，待核实所选模型支持情况”。已知该档不可用时根据实际支持集合调整并说明原因。none 仅在模型明确支持且任务适合关闭推理时评估使用。用户对耗时与资源消耗的偏好纳入选择。

推荐由用户选择采纳。实际调整设置需要用户授权及宿主支持，并记录真实结果。推荐完成即可继续已授权工作。验收覆盖简单任务、复杂故障、范围变化及可用档位未知四类场景，检查推荐依据与任务一致。

模型支持及推理预算机制以当前官方资料和宿主能力为准。资料核对日期为 2026-11-10。[OpenAI 推理模型文档](https://developers.openai.com/api/docs/guides/deployment-checklist)

## 执行指令与会话标题同步

日期：2026-11-10

状态：已写入 Skill 规则，真实宿主调用待验收

执行聊天收到授权指令后，以首行“开始执行”后面的完整内容作为会话标题，去除首尾空白和句末句号，保留圈号、项目名称、分隔符与任务名称。例如“开始执行② 轻量路线工作台 / B 路线与存储。”对应“② 轻量路线工作台 / B 路线与存储”。执行标题采用该规则，会话组织编号和固定绑定身份继续独立保存。

生成的 A/B/D 指令代码块携带具体目标标题及改名要求。执行聊天使用实际可用的 set_thread_title 修改自身名称并检查回执，当前聊天调用可省略 threadId。重复处理保持标题稳定，收到另一主步骤执行指令时按新首行更新。普通调试沿用当前标题。工具不可用或失败时记录实际结果并提供可复制标题，继续已授权工作。
