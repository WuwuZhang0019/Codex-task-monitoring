# 会话到面板的轻量路线管理指导方案

日期：2026-11-10

状态：指导方案；需求与规则整理完成，未进入实施

## 1. 文档定位

本文汇总本次讨论及用户提供的上一轮对话截图，记录产品方向、编号约定与交互规则。它是一般性指导方案，不是可执行方案，不包含开发任务派发、工期或已实现声明。后续需要另行制定可执行方案并核对实际代码。

本次编号与会话组织规则更新日期为 2026-11-10。总方案通过名称及固定 ID 识别，A、B、C 等字母用于总方案内的总步骤。既有 M、I、D、U 等历史记录按原标识保存，实施时建立新旧关联。

## 2. 产品目标与职责

简化“会话理解方案—传输步骤—面板显示状态”的过程。目标产品不需要内置 AI 工具、模型配置或第二套方案解析对话。

- Codex：读取可执行方案、提取步骤、报告执行进度、识别独立分支、编写后续方案。
- MCP：传递结构化路线、步骤、状态与分支信息，并支持读取已保存状态。
- 本项目：校验、存储、展示路线及状态，提示待规划分支，保存会话关联和变更记录。
- 用户：确认新分支的规划意图与后续执行范围。

面板显示的是 Codex 已通过 MCP 成功报告的进展，不是自动获知所有会话活动。没有更新、会话关闭或连接中断均不代表执行失败或完成。

## 3. 基本使用闭环

1. 用户在 Codex 中提供可执行方案；Codex 提取步骤编号、标题、执行内容及验收要求。
2. Codex 经 MCP 传入路线；有多少个正式步骤，就创建多少个站点，以线路按执行顺序连接。
3. 开始、完成、阻塞、取消或返工时，Codex 更新相应站点，面板展示状态、简短说明和最后更新时间。
4. 出现原方案外的独立事项时，Codex 登记来源站点、分支目标及阻塞关系，面板展示开放分支。
5. 分支在新会话中先展示一句规划意图，等待用户确认后再开展方案编写；方案形成后提取步骤，通过 MCP 补充路线。
6. 新会话接续前先读取现有路线及最新版本，避免重复建站或覆盖已发生的进展。

## 4. 编号与标识规则

### 4.1 编号定义

总方案统一编排 A、B、C、…、Z、AA、AB 等总步骤，编号在同一总方案内唯一。跨方案通过固定方案 ID 区分。工作树分配沿用总方案步骤编号。

| 对象 | 格式与示例 | 含义 |
|---|---|---|
| 总方案 | 制作示例任务看板 | 使用方案名称与固定方案 ID 识别 |
| 总步骤 | A、B、C | 总方案统一编排的执行单元，每个总步骤对应一个执行会话 |
| 细分步骤 | A-01、A-02 | 总步骤 A 内的具体任务，在 A 会话内执行 |
| 插入细分步骤 | A-02-a、A-02-b | 插入已有细分步骤之间的补充任务 |
| 补充事项分支 | A-01-01、A-01-02 | 从 A-01 产生的独立事项，记录来源及阻塞关系 |
| 分支工作树序号 | 1️⃣、2️⃣、3️⃣ | 执行资源的排列序号，与总步骤编号分别保存 |

总方案文档统一记录总步骤、细分步骤、验收要求、前置依赖、允许并行的步骤及工作树分配。一个工作树可以承接多个总步骤。同一总步骤的细分任务由对应会话完成，面板仍可分别展示和接收细分步骤状态。

独立补充方案通过名称与固定 ID 关联原事项分支，其内部总步骤从 A 开始编排。原事项分支保留来源标识和历史记录，跨方案关联使用方案 ID 与步骤 ID。

### 4.2 稳定性与排序

- 编号一经登记不重排、不复用；取消后仍保留历史编号。
- 在 A-02 与 A-03 之间增加步骤，使用 A-02-a；后续增加使用 b、c，超过 z 使用 aa、ab。
- 再次插入时仍分配下一个未用后缀，实际位置通过显式顺序保存，不依赖字符串排序。编号后缀表达分配顺序，线路表达执行顺序。
- 内部同时保存固定项目、方案、路线、步骤、分支和会话 ID。显示编号用于阅读和查找，状态更新以固定 ID 和版本校验定位。
- 方案修订沿用固定方案 ID 并递增版本；独立目标另建方案。涉及大幅拆分或替代时保留旧记录及替代关系，不覆盖历史完成证据。
- 本文作为指导方案保存，后续可执行总方案使用独立固定 ID 并关联本文。

## 5. 顺序执行与状态

每条工作树路线内部按显示顺序执行。跨工作树按总方案明确的依赖关系推进，无相互依赖的总步骤允许并行。前一步完成后才能开始下一步；取消步骤必须写明原因，并确认其取消不破坏后续前置条件。插入步骤也属于正式顺序约束，不能因后缀形式而跳过。

站点状态统一为待执行、执行中、已阻塞、已完成、已取消。已完成步骤需要返工时可重新进入执行中，并记录原因及历史完成记录；如果影响后续结果，应将受影响步骤标为待复核或阻塞说明，不能继续显示无条件完成。

站点保存进展说明、阻塞原因、更新时间及完成结果或交付物位置。有验收条件的步骤须满足条件后才能完成。断线只改变同步提示，不擅自修改业务状态。

## 6. 分支判定、规划与结束

### 6.1 何时创建分支

本节描述执行中产生的独立补充事项。总方案已规划的 Git 分支工作树按第 10 节分配总步骤，并记录各路线之间的前置依赖。

由 Codex 判断并报告，面板不分析聊天内容。完成原步骤所必需的普通调试、重试和小修复留在原站点；出现独立目标、需要单独安排或验收的事项才创建分支。

### 6.2 未规划分支

先保存固定分支 ID、显示编号、来源步骤、目标描述和阻塞关系，状态为待确认。面板从来源站点引出开放线路，不虚构步骤数量、完成百分比或固定终点；用于提示的开放端点不是正式步骤站点。

新会话标题示例：`[A-01-01] 权限管理方案待确认`。

新会话首条内容示例：

> 来自 A-01 的分支 A-01-01：接下来拟制定权限管理可执行方案，解决当前访问控制缺失问题；此分支阻塞 A-01，请确认是否开始制定方案。

此时等待用户确认，不直接编写完整方案或执行开发。用户确认制定方案后进入待规划；编写完成后依据用户已经授权的范围决定是否可以执行，不能将“同意写方案”解释为“同意全部实施”。

阻塞分支优先等待用户决策，来源步骤进入已阻塞；非阻塞分支登记后允许主线继续按顺序推进。提醒首次展示后保留待处理标记，不反复弹窗。

### 6.3 补充方案与结束

补充方案确认后登记方案名称与固定 ID，编排其总步骤并关联原事项分支。开放路线转为具有明确站点的路线，不重复创建同一分支。分支方案内部同样顺序执行。

分支结束须明确：回到来源步骤继续、接入明确的后续步骤，或作为独立事项结束。完成阻塞分支仅解除对应阻塞，不自动判定来源步骤已完成。分支可以取消或并回主线，但须记录原因及承接步骤；取消不能掩盖尚未解决的必要前置条件。

## 7. 完成判定

- 主线必需步骤及其验收要求未完成时，方案不能标记完成。
- 阻塞分支未解决时，方案不能标记完成。
- 主线完成但仍有非阻塞分支时，显示“主线已完成，另有待处理分支”，并显示数量与入口。
- 全部必需步骤完成，且各分支已完成、合理取消或被明确承接后，才能关闭整体路线；转交的未完成事项仍需可追踪。
- 会话结束、工具调用成功和交付物创建都不能单独代替方案验收。

## 8. MCP 与持久化原则

概念能力包括读取路线、导入或修订步骤、更新状态、登记分支、关联分支方案及关联会话；具体工具名称与数据结构由后续可执行方案确定。

传输至少能够表达项目与方案 ID、方案版本、来源文档、步骤固定 ID 与显示编号、标题及执行内容、显式顺序、状态、说明、更新时间、分支来源与阻塞关系、关联会话 ID。完成更新可携带交付证据。

- 导入先校验编号重复、引用缺失、顺序与结构，完整校验通过后提交，避免面板显示半条路线。
- 同一请求重试必须幂等，不能重复创建站点或分支。
- 更新携带版本，过期或乱序更新拒绝并返回当前状态，不采用静默覆盖。
- 发送失败保留待同步提示，成功确认后才显示已同步。
- 多会话操作同一路线以已存储版本协调，不能靠会话标题判断身份。
- 持久化保存路线、状态、关联与变更历史，重启后可恢复；备份与恢复策略后续落实。
- 方案修改保留修订差异；已开始或已完成步骤不能直接删除，应取消或建立替代关系。

### 8.1 信息方向与接收回执

补充日期：2026-11-10

采用“Codex 主动上报，工作台校验、保存和展示”的业务交互方式。首期不增加工作台主动向 Codex 派发执行、继续、重试或修改方案指令的流程。第 9、10 节的会话命名和归类仍属于独立的宿主操作能力。

每次上报应返回简短的保存回执，说明已保存、重复请求已处理或拒绝原因，并提供事件标识及已保存版本。回执只确认数据接收结果，不代表任务通过验收。超时或响应丢失时提交结果可能未知，应保留原事件标识进行查询或幂等重试，不能直接当作未保存。

保留 Codex 按需读取工作台已有路线及状态的能力，用于新会话接续、连接恢复、结束前核对和版本冲突处理；无需在每次上报后返回完整方案。

### 8.2 上报时机与粒度

| 时机 | 上报内容 |
|---|---|
| 首次登记方案 | 方案名称、来源、步骤编号、标题、顺序、执行内容及验收要求 |
| 任务本次执行开始 | 任务与会话关联、本次执行标识、准备执行的步骤及开始时间；一次逻辑开始事件 |
| 步骤状态发生变化 | 步骤开始、完成、阻塞、解除阻塞、取消或返工，以及原因或结果摘要 |
| 本次执行结束 | 结束原因、相关步骤最新状态、交付物、未完成事项及结束时间；一次逻辑结束事件 |
| 方案调整或出现分支 | 调整内容与原因、分支来源及阻塞关系，按既有授权范围处理 |

“开始一次、结束一次”指同一次执行的逻辑事件，网络重试不新增事件。重新发起执行使用新的执行标识，保留历史；同一次执行跨会话接续时沿用原执行标识并更新会话关联。

只发送任务开始和结束两次消息，无法展示执行过程中的站点位置，因此步骤切换和阻塞变化也需要补报。无需发送每次工具调用、逐条日志或模型内部思考。

本次执行结束与整个任务完成分别记录。结束原因可以是完成本次范围、等待用户、遇到阻塞、失败或取消；不能把会话停止或本次执行结束直接转换为路线完成。站点状态仍遵循第 5 节，整体完成仍遵循第 7 节。

### 8.3 专用 MCP 工具与调用规则

需要向 Codex 暴露专门用于结构化进度上报的 MCP tool。工具由工作台的 MCP 服务提供，Codex 调用；工具负责校验、持久化和返回回执，不自行理解聊天并判断步骤进展。

不必为每个步骤创建一个工具，也不预先要求新增一套与历史契约重复的接口。后续实施先核对既有 `workbench_record_start`、`workbench_record_blocker`、`workbench_submit_receipt` 等契约及实际能力，优先复用；如需统一状态上报入口，再明确其与既有工具的映射。此处确定功能职责，正式工具名称、数量和 schema 由可执行方案确定，本文不声明写入工具已接通。

上报输入至少应能表达项目、方案、任务、步骤和会话的固定标识、本次执行标识、唯一事件标识、事件类型、发生时间、预期版本、状态及简短说明。任务级事件可不指定单一步骤；完成事件携带结果与验收证据，阻塞事件携带原因、等待对象和恢复条件。服务端记录接收时间，并校验归属、授权、版本、顺序及允许的状态转换。

工具提供“如何上报”的接口，还需要执行规则或 Skill 明确“何时调用”：

1. 开始实际工作前，上报本次执行和当前步骤开始。
2. 检查步骤验收要求，满足条件后上报完成，再进入下一步骤。
3. 确实因外部信息、权限或用户决定而无法继续时，上报阻塞；普通调试、自动重试和必要的小修复仍保持执行中。
4. 阻塞解除或返工时，记录原因及状态变化，保留先前结果。
5. 正常结束本次执行前，核对已保存版本，补报相关步骤的状态快照和执行结果；快照同样经过版本与状态校验，不覆盖其他会话的新进展。

工具与调用规则需要共同落实。仅安装 MCP 工具不会自动捕获业务状态，单靠执行规则也不能保证所有变化都能成功上报。

### 8.4 漏报、异常中断与辅助观察

首期以 Codex 主动上报业务状态为主。宿主运行事件或会话观察能力可作为后续辅助来源，其可用性与覆盖范围必须实际验证；即使观测到运行、停止或断开，也不能据此判定业务步骤完成。

崩溃、强制停止或断线时可能无法发送结束事件。面板保留最后上报状态与更新时间，必要时显示“状态待确认”；长时间没有更新不自动判为失败或完成。尚未到达服务端的发送失败，需由发送侧保存待同步信息，面板不能宣称已经知道所有漏报。

恢复后先读取已保存状态，使用原事件标识查询或重试未确认的上报；确认当前版本后再补报缺失状态。不得伪造未观测到的结束时间或覆盖已有完成证据。后续实施需验证重复发送、响应丢失、乱序更新、多会话接续和异常中断后的恢复。

## 9. Codex 会话命名与关联

更新日期：2026-11-10

执行会话统一使用 `[总步骤编号] 简短主题`，例如 `[A] 数据准备`、`[B] 界面展示`、`[C] 交互验证`。每个总步骤对应一个执行会话，A-01、A-02 等细分步骤在 A 会话内连续执行。细分步骤的状态变化通过 MCP 上报到对应站点。

总步骤与会话绑定成功后，使用固定会话 ID 进行命名和归类。续接会话继续关联原总步骤及执行记录。重命名保持幂等，保留用户主题，并记录操作结果。宿主能力不足时提供建议名称及归类指引，实际自动创建、改名和移动能力在实施时验证。

## 10. Codex 侧栏项目与分支会话归类

更新日期：2026-11-10

### 10.1 管理目标

会话文件夹对应 Codex 侧栏项目。工作台保存总方案、总步骤、Codex 侧栏项目、会话、Git 分支及实际工作树目录之间的固定关联。总方案是步骤编排及依赖关系的统一来源。

### 10.2 命名与归类规则

总方案直接执行时，使用一个会话文件夹，名称为方案名。文件夹内按总步骤建立 A、B、C 等会话。

```text
制作示例任务看板
├─ [A] 数据准备
├─ [B] 界面展示
└─ [C] 交互验证
```

总方案拆分多个分支工作树时，每个分支工作树对应一个会话文件夹，名称为 `数字表情 方案名 · Git分支名`。先由总方案确定总步骤和依赖，再将总步骤分配到各工作树，所有会话沿用总方案编号。以下示例将 A—F 分配到三个工作树。

```text
1️⃣ 制作示例任务看板 · codex/mock-data
├─ [A] 数据准备
└─ [C] 数据校验

2️⃣ 制作示例任务看板 · codex/mock-ui
├─ [B] 界面展示
└─ [D] 界面完善

3️⃣ 制作示例任务看板 · codex/mock-validation
├─ [E] 交互验证
└─ [F] 结果汇总
```

A—F 表示总方案步骤，1️⃣—3️⃣ 表示工作树排列序号。执行先后及能否并行由总方案依赖决定。每个分支文件夹绑定其对应工作树实际路径，Git 分支名使用真实登记名称。

文件夹序号在同一总方案内按登记顺序分配并保持稳定。超过 9 时按各位数字组合，例如第 10 个使用 `1️⃣0️⃣`。工作台保存序号与侧栏项目固定 ID 的关联。方案名或 Git 分支名变化时，依据已确认关联更新文件夹名，并保存操作结果。

登记时优先复用已绑定的文件夹及序号，将总步骤会话归入其分配的工作树文件夹。每个细分步骤随所属总步骤执行，工作台通过固定 ID 保存和更新其状态。

### 10.3 自动化能力与接入要求

截至 2026-11-10，当前 Codex 宿主工具能够列出项目、将会话移入已有项目，以及重命名会话。额外源文件夹访问权限可能要求用户在侧栏完成移动操作。这些工具的可用范围属于当前宿主环境，独立工作台需要建立相应的授权调用通道。

自动创建和重命名 Codex 本地项目属于产品目标，具体接口仍待验证。后续实施需要确认宿主是否提供可调用的项目管理能力，以及同一路径多项目的保存、重启恢复和标题同步行为。能力接通前，工作台可提供建议项目名称、源文件夹路径和归类指引，由用户创建项目后绑定固定项目 ID，再继续执行可用的归类操作。

MCP 传输中应携带工作台业务项目、方案、分支、Codex 项目及会话的固定 ID 和关联信息。项目创建、改名及会话移动由接入的宿主能力完成，结果回传工作台保存。某项操作失败时保留已成功保存的关联与状态，提示失败环节并支持重试。

### 10.4 共享代码与并行工作

多个 Codex 侧栏项目关联同一个源文件夹时，其会话共享其中的代码文件。侧栏归类负责组织会话，代码隔离由工作树安排承接。多个开发分支需要同时修改代码时，应在后续可执行方案中明确各自工作树，并记录会话实际执行目录，便于区分业务分支、Codex 侧栏项目与 Git 分支。

## 11. 面板展示原则

主线按顺序连接，站点同时显示编号、简短标题和状态；详情展开后显示执行内容、验收要求、进展、证据和关联会话。分支从来源站点展开，并明确阻塞关系。

未规划分支展示开放末端和待确认或待规划提示；深层分支默认折叠但保留未完成数量。状态不能只靠颜色区分，应配文字或图标。面板显示最后更新时间与连接状态，区分已报告的事实与尚未同步的信息。

首期聚焦路线导入、顺序执行状态、分支登记与规划、会话关联和跨会话接续。复杂依赖图编辑器、面板内 AI 对话和自动推断未报告进展不属于本次目标。

## 12. 与既有项目的关系及后续边界

本方向收敛了内置 AI 与重复方案解析的职责，但本文不声明既有模块已移除或需要全部重写。后续制定可执行方案时，应先检查当前实现、既有 U 线交付、MCP 契约和持久化模型，确定复用、调整及迁移范围。

需要在实施方案中具体化的事项包括：编号登记与旧数据兼容、状态转换及顺序校验、分支确认记录、MCP 幂等和版本冲突、宿主会话操作能力、面板布局、持久化恢复及可验证验收条件。本文不直接派发这些工作，也不修改旧台账的完成状态。
