# A：会话到面板的轻量路线管理指导方案

日期：2026-11-10

状态：指导方案；需求与规则整理完成，未进入实施

## 1. 文档定位

本文汇总本次讨论及用户提供的上一轮对话截图，记录产品方向、编号约定与交互规则。它是一般性指导方案，不是可执行方案，不包含开发任务派发、工期或已实现声明。后续需要另行制定可执行方案并核对实际代码。

本方案编号为 A，属于本项目新的轻量路线方案编号体系。既有 M、I、D、U 等历史编号保留，不据此重编号、迁移数据或改变验收结论。本次仅落盘文档及调整当前讨论会话名称；不删除现有 AI 功能，不批量修改旧会话，不自动创建分支会话。

## 2. 产品目标与职责

简化“会话理解方案—传输步骤—面板显示状态”的过程。目标产品不需要内置 AI 工具、模型配置或第二套方案解析对话。

- Codex：读取可执行方案、提取步骤、报告执行进度、识别独立分支、编写后续方案。
- MCP：传递结构化路线、步骤、状态与分支信息，并支持读取已保存状态。
- 本项目：校验、存储、展示路线及状态，提示待规划分支，保存会话关联和变更记录。
- 用户：确认新分支的规划意图与后续执行范围。

面板显示的是 Codex 已通过 MCP 成功报告的进展，不是自动获知所有会话活动。没有更新、会话关闭或连接中断均不代表执行失败或完成。

## 3. 基本使用闭环

1. 用户在 Codex 中提供可执行方案；Codex 提取步骤编号、标题、执行内容及验收要求。
2. Codex 经 MCP 传入路线；有多少个正式步骤，就创建多少个站点，以线路按执行顺序连接。
3. 开始、完成、阻塞、取消或返工时，Codex 更新相应站点，面板展示状态、简短说明和最后更新时间。
4. 出现原方案外的独立事项时，Codex 登记来源站点、分支目标及阻塞关系，面板展示开放分支。
5. 分支在新会话中先展示一句规划意图，等待用户确认后再开展方案编写；方案形成后提取步骤，通过 MCP 补充路线。
6. 新会话接续前先读取现有路线及最新版本，避免重复建站或覆盖已发生的进展。

## 4. 编号与标识规则

### 4.1 编号定义

编号在工作台业务项目内唯一，跨业务项目通过项目 ID 区分。同一业务项目可以关联多个 Codex 侧栏项目，这些侧栏项目共用该业务项目的编号登记范围。统一使用半角连字符，字母大小写具有明确用途。

| 对象 | 格式与示例 | 含义 |
|---|---|---|
| 方案 | A、B、…、Z、AA、AB | 大写字母表示方案，按项目登记顺序分配 |
| 正式步骤 | A-01、A-02 | 方案编号加步骤编号；数字至少两位，超过 99 使用三位 |
| 插入步骤 | A-02-a、A-02-b | 插在 A-02 之后、原后续步骤之前；小写字母表示补充步骤 |
| 分支 | A-01-01、A-01-02 | 从 A-01 生出的第一个、第二个独立分支；末段是分支序号，不是分支步骤 |
| 插入步骤的分支 | A-02-a-01 | 从插入步骤 A-02-a 生出的第一个分支 |
| 分支方案步骤 | B-01、B-02 | 分支 A-01-01 补充方案后关联方案 B，其正式步骤使用 B 的编号 |

分支 A-01-01 的编号永久保留，关联方案 B 后不把分支改名为 B。这样分别表达“从哪里产生”与“由哪个方案承接”。B-02 再产生分支时使用 B-02-01，不无限拼接祖先编号。一个步骤可产生多个分支，各自独立登记。

### 4.2 稳定性与排序

- 编号一经登记不重排、不复用；取消后仍保留历史编号。
- 在 A-02 与 A-03 之间增加步骤，使用 A-02-a；后续增加使用 b、c，超过 z 使用 aa、ab。
- 再次插入时仍分配下一个未用后缀，实际位置通过显式顺序保存，不依赖字符串排序。编号后缀表达分配顺序，线路表达执行顺序。
- 内部同时保存固定项目、方案、路线、步骤、分支和会话 ID。显示编号用于阅读和查找，状态更新以固定 ID 和版本校验定位。
- 方案修订沿用方案编号并递增版本；独立目标另建方案。涉及大幅拆分或替代时保留旧记录及替代关系，不覆盖历史完成证据。
- 本文 A 是指导方案，不因获得编号就生成执行站点；未来可执行方案取得新的方案编号并关联本文。

## 5. 顺序执行与状态

每条路线必须按显示顺序执行，不默认支持同一路线内并行。前一步完成后才能开始下一步；取消步骤必须写明原因，并确认其取消不破坏后续前置条件。插入步骤也属于正式顺序约束，不能因后缀形式而跳过。

站点状态统一为待执行、执行中、已阻塞、已完成、已取消。已完成步骤需要返工时可重新进入执行中，并记录原因及历史完成记录；如果影响后续结果，应将受影响步骤标为待复核或阻塞说明，不能继续显示无条件完成。

站点保存进展说明、阻塞原因、更新时间及完成结果或交付物位置。有验收条件的步骤须满足条件后才能完成。断线只改变同步提示，不擅自修改业务状态。

## 6. 分支判定、规划与结束

### 6.1 何时创建分支

由 Codex 判断并报告，面板不分析聊天内容。完成原步骤所必需的普通调试、重试和小修复留在原站点；出现独立目标、需要单独安排或验收的事项才创建分支。

### 6.2 未规划分支

先保存固定分支 ID、显示编号、来源步骤、目标描述和阻塞关系，状态为待确认。面板从来源站点引出开放线路，不虚构步骤数量、完成百分比或固定终点；用于提示的开放端点不是正式步骤站点。

新会话标题示例：`[A-01-01] 权限管理方案待确认`。

新会话首条内容示例：

> 来自 A-01 的分支 A-01-01：接下来拟制定权限管理可执行方案，解决当前访问控制缺失问题；此分支阻塞 A-01，请确认是否开始制定方案。

此时等待用户确认，不直接编写完整方案或执行开发。用户确认制定方案后进入待规划；编写完成后依据用户已经授权的范围决定是否可以执行，不能将“同意写方案”解释为“同意全部实施”。

阻塞分支优先等待用户决策，来源步骤进入已阻塞；非阻塞分支登记后允许主线继续按顺序推进。提醒首次展示后保留待处理标记，不反复弹窗。

### 6.3 补充方案与结束

方案确认后分配独立方案编号，提取步骤并关联原分支。开放路线转为具有明确站点的路线，不重复创建同一分支。分支方案内部同样顺序执行。

分支结束须明确：回到来源步骤继续、接入明确的后续步骤，或作为独立事项结束。完成阻塞分支仅解除对应阻塞，不自动判定来源步骤已完成。分支可以取消或并回主线，但须记录原因及承接步骤；取消不能掩盖尚未解决的必要前置条件。

## 7. 完成判定

- 主线必需步骤及其验收要求未完成时，方案不能标记完成。
- 阻塞分支未解决时，方案不能标记完成。
- 主线完成但仍有非阻塞分支时，显示“主线已完成，另有待处理分支”，并显示数量与入口。
- 全部必需步骤完成，且各分支已完成、合理取消或被明确承接后，才能关闭整体路线；转交的未完成事项仍需可追踪。
- 会话结束、工具调用成功和交付物创建都不能单独代替方案验收。

## 8. MCP 与持久化原则

概念能力包括读取路线、导入或修订步骤、更新状态、登记分支、关联分支方案及关联会话；具体工具名称与数据结构由后续可执行方案确定。

传输至少能够表达项目与方案 ID、方案版本、来源文档、步骤固定 ID 与显示编号、标题及执行内容、显式顺序、状态、说明、更新时间、分支来源与阻塞关系、关联会话 ID。完成更新可携带交付证据。

- 导入先校验编号重复、引用缺失、顺序与结构，完整校验通过后提交，避免面板显示半条路线。
- 同一请求重试必须幂等，不能重复创建站点或分支。
- 更新携带版本，过期或乱序更新拒绝并返回当前状态，不采用静默覆盖。
- 发送失败保留待同步提示，成功确认后才显示已同步。
- 多会话操作同一路线以已存储版本协调，不能靠会话标题判断身份。
- 持久化保存路线、状态、关联与变更历史，重启后可恢复；备份与恢复策略后续落实。
- 方案修改保留修订差异；已开始或已完成步骤不能直接删除，应取消或建立替代关系。

## 9. Codex 会话命名与关联

本节要求在用户实际使用产品时自动执行。方案编号确定且关联会话绑定成功后，系统应触发重命名，在该用户的 Codex 会话标题前添加编号。当前讨论会话的改名仅是一次操作记录，产品仍需实现这一持续行为。

建议在方案登记或发布成功后触发，使用固定会话 ID 定位目标，读取原标题，生成带编号前缀的标题，再调用宿主的会话重命名能力。已有相同前缀时保持幂等，编号绑定变更时替换旧前缀，并保留主题文字。记录成功、失败与重试状态。

技术依据核对日期为 2026-11-10。Codex App Server 提供 `thread/name/set` 设置会话名称及 `thread/name/updated` 通知。产品可通过与目标会话存储匹配的 App Server 连接或宿主暴露的重命名工具完成调用。MCP 负责传递方案与会话关联信息，重命名由接入的宿主能力执行。实施时需要验证用户桌面现有会话的可访问性及侧栏标题同步效果。官方依据见 [Codex App Server](https://learn.chatgpt.com/docs/app-server)。

统一格式为 `[确定好的编号] 简短主题`，前缀位于会话名称最前面。

| 会话用途 | 示例 |
|---|---|
| 方案整体讨论 | [A] 简化会话到面板状态流程 |
| 单步骤执行 | [B-01] 实现路线接收 |
| 插入步骤执行 | [B-02-a] 补充字段校验 |
| 未规划分支讨论 | [B-01-01] 异常恢复方案待确认 |
| 分支方案形成后的整体讨论 | [C] 异常恢复方案 |

分支方案形成后可将该讨论会话的前缀更新为新方案编号，同时保留其分支关联记录。一个会话涉及多个步骤时，优先使用方案编号；单步骤专用会话使用步骤编号。不要为每次状态更新反复改名。

重命名只更新已确认绑定的会话，替换已有编号前缀而不是不断叠加。后台使用会话固定 ID 关联，不从标题反向猜测归属。重命名失败单独提示并允许重试，不回滚已经保存的路线。

分支采用新会话承接是目标流程；实际自动创建、写入首条说明和重命名是否可用，必须在实施时核对宿主能力。无能力时提供可复制的标题与描述，由用户打开会话，不能伪称已创建。本次只调整当前会话，不创建真实分支会话。

## 10. Codex 侧栏项目与分支会话归类

日期：2026-11-10

### 10.1 管理目标

用户截图中的会话文件夹对应 Codex 侧栏的本地项目。用户可以为同一个源文件夹建立多个侧栏项目，将不同方案及分支的会话分别收纳。工作台应记录这些项目的关联，支持在路线、站点与对应会话之间跳转。Codex 项目与源文件夹的概念依据见 [Projects and chats](https://learn.chatgpt.com/docs/projects)。

工作台业务项目负责统一登记方案与分支。其下的多个 Codex 侧栏项目分别承接主线或分支会话，使用各自固定的 Codex 项目 ID，同时可以关联相同源文件夹路径。

### 10.2 命名与归类规则

| 归类对象 | Codex 侧栏项目名称 | 收纳会话示例 |
|---|---|---|
| 主线方案 | [A] 主线方案 | [A] 方案讨论、[A-01] 步骤一、[A-02] 步骤二 |
| 来源于 A-01 的分支 | [A-01-01] 权限管理分支 | [A-01-01] 方案待确认，形成方案 B 后承接 [B] 方案讨论、[B-01] 第一步等会话 |

分支侧栏项目保留来源分支编号，形成独立方案后，其内部会话使用第 9 节的方案或步骤编号。工作台保存分支与承接方案之间的对应关系。项目标题变化时依靠固定 ID 维持关联。

用户首次采用该组织方式后，方案或分支登记时查找已绑定的侧栏项目。已绑定则复用，需要新项目时按已确定的编号和主题命名并关联源文件夹，再将会话归入目标项目。重试时应复用已经创建成功的项目。自动改名应保留用户主题，仅更新工作台管理的编号前缀，并保存操作结果。

### 10.3 自动化能力与接入要求

截至 2026-11-10，当前 Codex 宿主工具能够列出项目、将会话移入已有项目，以及重命名会话。额外源文件夹访问权限可能要求用户在侧栏完成移动操作。这些工具的可用范围属于当前宿主环境，独立工作台需要建立相应的授权调用通道。

自动创建和重命名 Codex 本地项目属于产品目标，具体接口仍待验证。后续实施需要确认宿主是否提供可调用的项目管理能力，以及同一路径多项目的保存、重启恢复和标题同步行为。能力接通前，工作台可提供建议项目名称、源文件夹路径和归类指引，由用户创建项目后绑定固定项目 ID，再继续执行可用的归类操作。

MCP 传输中应携带工作台业务项目、方案、分支、Codex 项目及会话的固定 ID 和关联信息。项目创建、改名及会话移动由接入的宿主能力完成，结果回传工作台保存。某项操作失败时保留已成功保存的关联与状态，提示失败环节并支持重试。

### 10.4 共享代码与并行工作

多个 Codex 侧栏项目关联同一个源文件夹时，其会话共享其中的代码文件。侧栏归类负责组织会话，代码隔离由工作树安排承接。多个开发分支需要同时修改代码时，应在后续可执行方案中明确各自工作树，并记录会话实际执行目录，便于区分业务分支、Codex 侧栏项目与 Git 分支。

## 11. 面板展示原则

主线按顺序连接，站点同时显示编号、简短标题和状态；详情展开后显示执行内容、验收要求、进展、证据和关联会话。分支从来源站点展开，并明确阻塞关系。

未规划分支展示开放末端和待确认或待规划提示；深层分支默认折叠但保留未完成数量。状态不能只靠颜色区分，应配文字或图标。面板显示最后更新时间与连接状态，区分已报告的事实与尚未同步的信息。

首期聚焦路线导入、顺序执行状态、分支登记与规划、会话关联和跨会话接续。复杂依赖图编辑器、面板内 AI 对话和自动推断未报告进展不属于本次目标。

## 12. 与既有项目的关系及后续边界

本方向收敛了内置 AI 与重复方案解析的职责，但本文不声明既有模块已移除或需要全部重写。后续制定可执行方案时，应先检查当前实现、既有 U 线交付、MCP 契约和持久化模型，确定复用、调整及迁移范围。

需要在实施方案中具体化的事项包括：编号登记与旧数据兼容、状态转换及顺序校验、分支确认记录、MCP 幂等和版本冲突、宿主会话操作能力、面板布局、持久化恢复及可验证验收条件。本文不直接派发这些工作，也不修改旧台账的完成状态。
